# 三个插件分别是什么

> 每个包：它给谁用 · 它做什么 · 它怎么判断 · 它不做什么 · 它的配置

---
## 一、`dsh-bulletin-dispatch` —— 跨桌投递（必须先装这个）

给谁用：所有会话。
它做什么：让"桌"这个概念成立，然后让桌与桌之间能互相发单子。

### 1. 认桌

**从会话标题的 `NN-` 前缀认出这是哪张桌。**

```
会话标题 = "02-环境维护"     ⇒ 桌 02
会话标题 = "随便聊聊天"       ⇒ ⛔ 认不出 ⇒ 它还不是办公室成员
```

⚠️ "认不出"意味着什么：

| | |
|---|---|
| ✅ **它照收公告** | 公告是广播 —— 入口不该关（新会话要靠它才知道有这间办公室、才知道该改标题） |
| ⛔ **它收不到单子** | 不知道它是谁，就不能把活交给它 |
| ⛔ 它不记进「认过桌的会话」 | 这一档是新加的 —— 原来会把它记成一个叫"办公室"的桌 |

为什么第三档要砍掉：它原来会被记成"办公室" ⇒
在状态表里看起来像个成员，而它其实取不到任何单子。
⇒ 那种"半个身份"比没有身份更坏。

为什么靠标题而不是工作目录：因为"桌"不是平台概念 ——
平台的会话只有"工作目录"和"会话号"。多张桌共用一个工作目录是很正常的事
（我这里就是这样），所以**不能用目录区分**。
⚠️ 而且**标题是"平台侧的事实"，不是 AI 自己说的** —— 见 [`03`](03-机制详解.md) 零点七。

改标题由用户点头：认不出桌时，插件会提议一次（"把标题改成 `NN-名字` 就行"），
**但绝不会自己去改用户的标题**。

### 想换桌？改标题里的编号就行

因为"**编号就是地址**" —— 把标题从 `02-环境维护` 改成 `03-本地电脑维护`，
这个会话下一轮就是 03 桌了（它开始收 03 的单子）。

⚠️ 而有两件事要说清：

| # | 事 |
|---|---|
| 1 | 只改名字、不动编号（`03-本机电脑维护` → `03-本地电脑维护`）⇒ **桌号不变** —— 名字是称呼，编号才是地址 |
| 2 | 手动改编号 ⇒ **换桌**（和用插件的改名工具改，结果一样）—— "编号就是地址"，两条路不该给出不同答案 |

⚠️ 而"换桌"之后先前那些单子怎么办（这是当初不敢让它换桌的理由）：

> **单子挂在桌号上，不挂在会话上。**
> ⇒ 换到 03 之后，它取 03 的单子；先前那些 02 的单子留在那儿，等 02 桌别的会话来取。
> ⇒ **已经取走的、正在做的，全都不受影响。**

### 2. 发单子（指针型）

```
发单({ 目标桌, summary: "一句话说清是什么", ptr: "详见哪里" })
```

单子会长在对方的系统提示里（不占消息流），长这样：

```
跨桌投递：本桌有 N 张待取的单子（桌 04）
· 来自 桌 02（09-30 13:47）：一句话 —— 详见 `00-通用\信箱\04\…`
取走后本桌其它会话不会再看到它。要用就用，不用就放过 —— 不需要回执。
```

> ⚠️ 上面是插件注入的原话 —— 里面的「本桌」指的是收到这条提示的那个会话所属的桌。
> （不是某个内部术语，就是"你这一桌"的白话说法。）

语义（每一条都是刻意的）：

| 语义 | 为什么 |
|---|---|
| ⭐⭐ 只有"认过桌的会话"收得到 | ⚠️ 这一条最容易被误会成"会乱投" —— 见下面那张对照表 |
| 地址必须是"一个桌号" | `dispatch_ticket` 的目标只认编号（`01`～`99`）。**填"办公室"会被直接拒绝** —— 那就是公告，而且没有人会来取这种单子 |
| 谁的：挂在"桌"上 | 不是发给某个会话的 —— 会话会结束、会压缩、会重开 |
| 谁先来谁取走 | 同桌多个会话 ⇒ 先跑到那个取走 ⇒ 同一轮里不会两个人都领到它（⚠️ **不是"全局恰好一次"** —— 抢占记在进程内，取走写失败后重启可能重投，见 [`03`](03-机制详解.md) §"不重复干活"） |
| 取走之后同桌看不到 | 否则每个会话都会去干一遍 |
| 压缩不影响 | 会话号不变 ⇒ 不会因为压缩而重复送达 |
| 不需要回执 | 见根 README 的"刻意的'不做'" |
| 不跟踪做没做完 | 同上 |

### ⭐⭐ 而投递和公告的送达范围正好相反（这一条最容易误会）

| | 投递（单子） | 公告 |
|---|---|---|
| 送给谁 | ⛔ **只有认过桌的会话** —— 会话标题带 `NN-` 前缀的那些 | ✅ 这台电脑上的所有 DSH 会话（**一次性会话、子代理、没认过桌的都收得到**） |
| 怎么送 | 按桌路由：单子挂在桌号上，同桌谁先来谁取走 | 广播：每个会话看到的是同一份 |
| 认不出桌时 | 收不到、也不会被投 | 照收（只是发布时署不上名） |
| 为什么这样 | 不知道它是谁，就不能把活交给它 —— 投错了就是"一张给 03 桌的单子落在只是路过的会话里，没人真的处理" | 公告是入口：新会话要靠它才知道有这间办公室、才知道该把标题改成 `NN-名字` —— 入口不该关 |

⇒ 一句话：投递是"派活"，只派给认识的桌；公告是"广播"，谁都听得到。
⚠️ 所以"投递会不会乱投"这个担心不成立 ——
它连"不认识"的会话都到不了，更不会投给别的桌（路由就是按桌号走的）。

### 3. 送达状态表（派生视图）

**状态一变就重写一份给人看的 markdown**（⚠️ **不是"定期生成"** —— 没有定时器；
投递、取走、认桌、回收这些动作发生时它当场重写）：待取的单子 · 已被取走的 · 最近的取走记录 ·
认过桌的会话 · 健康（插件版本 / 存储 / 落盘确认）。

⛔ **它只由插件写** —— 文件头上就写着"不要手改，改了会被覆盖"。

⚠️ 其中两张表有「谁投的」这一列：
它们原来只有"目标桌"、没有发起方 ⇒ 读的人只能猜"这张单子是谁发起的"
（而且真的有人猜错了，见 [`06-经验与教训.md`](06-经验与教训.md) 误判四）。

| 列 | 值长什么样 | 备注 |
|---|---|---|
| 谁投的 | `桌 04（插件事务）` | ⚠️ 这个形状是前端解析得出来的前提 —— 改之前要问面板 |
| 目标桌 | 同上 | |
| 谁取走的 / 取走的会话 | `桌 02（环境维护） · 02-环境维护` | 桌 + 会话标题；查不到会话就退回会话号 |
| 会话号那一列（在"认过桌的会话"表里） | `…e5643720e487` | 只留尾部，够认出是谁 |

一条从实战里来的规矩（值的格式不是自由的）：

> 谁取走的那一列，写的是"桌 + 会话标题"而不是光一个会话号 ——
> 因为没人认得会话号（*"只有会话编号，有的不太好看"*）。
> ⇒ **给人看的表，要写人认得出的东西。**

⚠️ 而"谁投的"这一列有个数据来源的细节：
取走历史里新记录自带 `source`，老记录没有 ⇒ 渲染时去单子表兜底查；
两条都没有就写 `—`（诚实地说"不知道"，不猜一个桌号出来）。

### 4. 会话回收

问题：用户删掉一个会话之后，它只是不再跑 —— 记录会永远留在表里，
状态表上一直列着一个已经不存在的东西。

做法：定期问平台"现在还有哪些会话"（`sessionQuery.listSessions()`），
表里不在名单上的就清掉。

⚠️ 一条踩过的坑：别自己去维护一个"我见过它活着"的集合 ——
结果进程一重启集合就空了 ⇒ 那个判据永远不工作，而且一声不响。
⇒ **判据要"问平台"，不要"自己记"**（自己记的状态 = 又一个会过期的副本）。

⚠️ **而"清掉"不是立刻的** —— 这一点很容易被当成"坏了"：

| 为什么慢 | 具体 |
|---|---|
| **节流** | 回收挂在"每轮开始前"、**全局**节流一次（`sweepIntervalMs`，默认 10 分钟，可配）—— 列名单是**异步**的，不能每步都全查 |
| **得有人动** | 它挂在 pre-step 上 ⇒ 一张桌都不在跑的时候，它不会被调度 |
| ⚠️ **刷新面板没用** | 面板那个"刷新"只是**重读状态表文件**；而状态表是**回收真删掉东西之后**才重写的 ⇒ 文件还没变，刷多少次都一样 |

⇒ 删掉一个会话之后，名册**最长滞后一个节流周期**才跟着消失 —— 等它跑过就好，不用去点刷新。

> **想知道现在是多少、或想立刻让它跑一次**：投递插件带了个诊断工具 `sweep_sessions` ——
> 它会**自报当前节流值**（毫秒），而且**绕过节流立刻跑一次**（只报告，不删东西）。

### 5. 子代理不算"桌"

子代理的标题是它收到的提示词开头（比如"你是一个独立的技术评审…"），
⇒ 认桌认不出它 —— 而"认不出"意味着什么，见下：

| | 原来 | 现在 |
|---|---|---|
| 认不出时 | 把它记成一个叫"办公室"的桌 | 什么都不记（它还不是办公室成员） |
| 后果 | ⚠️ 只要子代理跑过，状态表里就多一行"办公室" | ✅ 名单是干净的 |

⇒ 判据：**有 `parentSession` 的会话（＝子代理）直接不认。**
（用平台自己标的血缘，不要去猜会话号里有没有某个前缀 —— 那是巧合，不是契约。）
⚠️ 而那是"第一道"闸 —— 就算它漏了，"认不出就不记"那道闸也不会让子代理污染名单。

### 配置（节选）

> ⚠️ **配置写在你自己 profile 的 `cordis.patch.yml` 里，不要写进插件目录**
> （理由见 README「快速开始」那一节）。

| 键 | 默认 | 说明 |
|---|---|---|
| `workspaceRoot` | ⚠️ 没有默认值 | **必填** —— 你的共享目录根。没配 ⇒ 状态表不装配并出一条警告 |
| `features.identity` | `true` | 认桌 |
| `features.sessionGc` | `true` | 会话回收 |
| `features.dispatch` / `dispatchTools` / `status` | `true` | 投递 / 工具 / 状态表 |
| `features.proposeRename` | `true` | 认不出桌时提议一次改名 |
| `deskNames` | `{}`（空） | 桌号 → 桌名。只影响显示（状态表里写成名字而不是号码），认桌不靠它 |
| `identityNotice` | 一句话 | 认桌成功后注入的那句（`{desk}` / `{title}` 会被替换） |
| `statusFile` / `stateFile` / `debugLog` | — | 三个文件的位置（`statusFile` 留空时由 `workspaceRoot` 推） |
| `sweepIntervalMs` | `600000` | 会话回收的节流（`0` = 关掉） |

⚠️ 关于 `deskNames`，一个容易误会的地方：

| 容易以为的 | 实际 |
| --- | --- |
| 它预置了四张桌（`{01…04}`） | 默认是 `{}`（空的） —— 不预置任何桌名 |
| "这个你肯定要改" | 不改也能跑 —— 它只影响显示；**认桌靠的是会话标题的 `NN-` 前缀**，和这张表无关 |

⇒ 想让它显示得更顺眼就填，不填也不影响功能。

## 二、`dsh-bulletin-announce` —— 办公室公告频道

给谁用：所有会话 + 用户。
它做什么：让"办公室最近发生了什么"能广播一次、所有人只看到一次。

### 机制

| 部分 | 说明 |
|---|---|
| 公告文件 | 一个纯文本文件，一行一条：`- MM-DD｜发布者｜一句话｜详见｜有效期`。规矩按角色写：**AI 只能追加，用户可以删改**（见 [`01`](01-思路.md) §五.二） |
| 发布 | 会话通过 `announce` 工具追加一行；⚠️ "只有用户能批准"是约定（见 [`03`](03-机制详解.md) 那节的照实说明） |
| 送达 | 每个会话记一组"见过的条目指纹"；开桌时补看"仍在有效期内的"（⚠️ 有数量上限，默认一次最多列 8 条，超了只报"还有 N 条"）、之后只推新增的 |


### ⚠️ 最容易误解的一处：它不是"游标"，是"内容指纹"

一个很自然的猜测：*"每个会话一个游标（读到第几行）；开桌时推『从来没见过的』条目"*。

⇒ 而实际不是"读到第几行"，而是**每个会话存一组"见过的内容指纹"**（`sha1(那一行)` 的前 16 位）：

| | 游标（那个自然的猜测） | 内容指纹（实际做的） |
|---|---|---|
| 记什么 | 读到第几行 | 见过哪些内容 |
| 文件被编辑过 | ⚠️ 行号会错位 ⇒ 可能漏、可能重 | ✅ 不受影响（指纹认的是内容） |
| 开桌时 | 从"当前位置"往后看 | 补看"仍在有效期内的"（⚠️ 有上限：默认 8 条，见上面那张表） |
| 压缩上下文后 | 游标不变 ⇒ 不重复 | **清空重发**（因为"见过的"随上下文一起没了） |

代码注释里有**一句话**把这个说清了（它比这一整节都短）：

> "游标代表『读者现在还记得什么』，不是『文件里发过什么』。"

⇒ 这就是为什么必须记"内容"而不是"位置"：
上下文被压缩之后，"记得什么"变了，而"文件里发过什么"没变 ——
按位置记的游标对此一无所知。

### `/mute` 与 `/unmute`

> ⚠️ **先说清范围：静音是"这一个会话"的事，不是全局的。**
> 它按会话号记（一份静音文件，里面一个一个 `sessionId`）——
> **⇒ 你在 A 会话里 `/mute`，B 会话照常收公告。**

| 命令 | 作用 |
|---|---|
| `/mute` | **只静音当前这个会话**：停注入（账冻住不动 —— **不推进"见过"记录**） |
| `/unmute` | 恢复注入，把静音期间积压的、仍在有效期内的那些补给你 |

**⚠️ 而"全局静音"这个能力并没有消失** —— 它是配置里的 `enabled: false`（对所有会话都不注入）。
两者的区别是：**`/mute` 解除时会把积压补上**，`enabled: false` **不会**（它压根没记游标）。

⚠️ 而"补给"有个上限（和平时一样）：**一次最多展开 8 条**，
超出部分只报"还有 N 条"+ 文件位置；**过期的不再送** —— 需要完整内容就直接读公告文件。

⇒ 所以准确的说法是：静音只是"晚一点知道"，不是"永远不知道" ——
⚠️ 但也不是"一条不漏地全塞给你"，它受有效期和单次显示上限两道限制。

### 谁能改已有的行

只有用户本人。 各桌只往末尾加。
—— 这条不是靠插件拦（拦不住：那是个纯文本文件），
是靠约定 + 把"发布/编辑"这件事在面板上做成一个按钮（见面板那节）。

⚠️ 而"只有用户能改"**是一条约定，不是一道闸门** —— 实际有三个写入口：

| # | 写入口 | 技术闸门 |
|---|---|---|
| 1 | 面板（发布 / 编辑 / 删除按钮） | ⚠️ **发布没有确认框**（点了就提交）；**编辑和删除有**（编辑先看"改前 / 改后"对照）。另有乐观锁：`revision` 对不上就拒 |
| 2 | `announce` 工具（任何一张桌都能调） | ⚠️ 没有 —— 只在工具说明里写"先征得用户同意" |
| 3 | 直接改那个文件 | ⚠️ 没有（它就是个纯文本文件） |

⇒ 面板是唯一把这条约定做成结构的地方，但别把它当成一道闸门来依赖。

### 配置（节选）

**必填两项**：`workspaceRoot` · `announcementFile`。
⚠️ **而没配的后果和投递那个不一样** —— **它不会拒绝启动**，
**症状是"读不到公告 ⇒ 各桌静默收不到"**，调 `announce` 发布时才抛错。

| 键 | 默认 | 说明 |
|---|---|---|
| `workspaceRoot` | ⚠️ 没有默认值 | 必填 |
| `announcementFile` | ⚠️ 没有默认值 | 必填 —— 公告文件的完整路径 |
| `hint` | 一句话 | 注入时附的"指路"（**只在开桌 / 压缩后重发时出现**；留空 = 不附）<br>⚠️ **默认那句只说"有一份办公室根 README、先读它"** —— **它不假设你那份 README 长什么样** |
| `enabled` | `true` | 全局开关 |
| `maxPerInjection` | `8` | 单次最多展开几条（超出的只报数量） |
| `defaultTtlDays` | `14` | 条目没写有效期时的天数 |
| `publisherNames` · `fallbackPublisher` | — | 工作区 → 发布者显示名；推导不出来时用哪个 |
| `titlePrefix` · `resendNote` · `mutedNotice` · `debugLog` | — | 注入首行 / 压缩重发那句 / 静音提示 / 诊断日志 |

**⚠️ 三个包的完整最小配置**（可以照抄的那种）在 [`README`](../README.md) 的「快速开始」§4 —— **这里不重抄一份**（抄两份就会分叉）。

## 三、`dsh-bulletin-panel` —— 侧边栏卡片

给谁用：用户（这是唯一一个"为人做的"部件）。
它做什么：把公告和投递状态放进 GUI 的右侧栏，并让用户能从界面发布/编辑公告。

### ⚠️ 依赖第三方

**它必须有 [`dsh-better-sidebar`](https://www.npmjs.com/package/dsh-better-sidebar) 才出得来** ——
卡片是注册到那个插件提供的 `ctx.betterSidebar.registerTab` 上的。

⇒ 只装本包不会出现卡片。

### 它读什么

```
GET /sidebar/api/office                公告（已解析成条目 + 文件指纹 revision）+ 状态表原始 markdown
                                       + 版本号 + 见过数（问公告插件的只读接口要来的）
GET /sidebar/api/office/deletions      ⭐ 删除记录（面板「健康」页把它画成一条时间线）
```

返回：公告（已解析成条目 + 一个文件指纹 `revision`）· 状态表（原始 markdown，前端自己渲染）。

### 它能写什么（只有公告）

```
POST /sidebar/api/office/announce          追加一条公告
POST /sidebar/api/office/announce/edit     改一条已有的（逐字核对原文）
POST /sidebar/api/office/announce/delete   删掉一条
```

⚠️ 删除那条的响应里带 `logged`（删除记录写上了没有）——
因为 "删成功"和"记账成功" 是两件事：记账失败**不否定删除**（它只打一行 warn），
⇒ 而它真的静默失败过（⚠️ 一次**变量名撞车**引出来的，细节见 [`06`](06-经验与教训.md)）。
加了 `logged` 前端就不用猜了。

⛔ **它绝不写"送达状态表"** —— 那是派生视图（投递插件生成的），
面板写它就是第二个真相源。

### 它还能删公告，而删除不是"例外"

规矩是按角色写的：AI 只能追加；用户可以删改（见 [`01`](01-思路.md) §五.二）——
⇒ 删除属于"用户那一半"，它不是破例，是规矩里本来就有的东西。

⚠️ 而它的代价要照实说：**已经见过那条的会话不会收到任何信号。**
所以面板删之前会告诉你有几个会话的见过记录里有这条，删之后往 `公告-删除记录.md` 追一行。
为什么做"真删"而不做"撤回"、以及那三档数字怎么来的：见 [`docs/07`](07-可视化面板.md) §三。

### 五条护栏（写在这儿给想改代码的人看）

> `07` 那边只列了 4 条（它把"删除要有据"归到 §三 去讲了）。
> ⇒ 这里列全，并和 `07` 交叉引用。

| # | 护栏 | 为什么 |
|---|---|---|
| 1 | ⭐ 原子写（先写临时文件 → `rename`） | 公告文件是各桌获取办公室信息的唯一入口。半截文件 = 各桌再也收不到公告 = 事故。<br>⚠️ **删除记录也走原子写**（不是 `appendFileSync`）—— 理由同上：记到一半崩了，下半截永远补不回来 |
| 2 | ⭐⭐ 两道乐观锁 | ① `revision` = 整个文件的指纹 ② 编辑/删除时逐字等于文件里那一行。**任何一道对不上就拒绝**，绝不猜"大概是想改那条吧" |
| 3 | 只认本机 + 同源 | 防的不是"黑客"，是你浏览器里别的网站顺手发个请求 |
| 4 | ⭐ 删除要"有据" | 删之前告诉你"有几个会话的见过记录里有这条" —— ⚠️ 那个数字是问公告插件的只读接口要来的（`GET /sidebar/api/announce/seen`），面板不自己读它的存储。<br>⭐ 而"有据"还有第二半：删完的响应里带 `logged`（删除记录写上了没有）—— "删成功"和"记账成功"是两件事。完整的前因后果见 [`07`](07-可视化面板.md) §三 |
| 5 | `allowWrite: false` 一键退回纯只读（**包括删除**） | 有些环境就是不该让面板写 |

> ⚠️ 还有一条"反直觉的护栏"（它不算上面五条，但它决定了上面几条管不管用）：
> 平台的**审批服务在"完全权限"模式下会静默通过** ⇒ 它拦不住误点。
> ⇒ 所以"只有用户能改"不能靠平台拦，得靠界面本身长得不像日常动作 + 确认框 + 乐观锁。

另外：编辑时**日期和发布者保持原样**（改内容 ≠ 改发布日期）。

### 为什么"只有用户能改"

不是靠登录，也不是靠审批机制 —— 而是：

```
这是用户专用的界面  ＋  编辑要确认（界面上的确认框）  ＋  两道乐观锁
```

> ⚠️ 一个反直觉的事实：DSH 平台有审批服务，但在"完全权限"模式下
> 审批会静默通过 ⇒ 等于没拦。所以"确认"只能靠界面上的确认框 —— 那才真拦得住误点。
