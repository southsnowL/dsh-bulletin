# 机制详解：一轮协作长什么样

> 根 README 讲了想法；这份讲它实际怎么运转 —— 谁在什么时候写什么、读什么。

---

## 零、⭐ 先说"为什么要认桌"（这是整套东西的起点）

很多人第一反应是"为什么每个会话都要认个桌？" —— 因为不是所有会话都该参与办公室。

### 会话是分两种的

| 那种会话 | 例子 | 该进办公室吗 |
|---|---|---|
| 有意义的长期会话 | "前端"、"环境维护"、"插件事务" —— 你会反复回来、它要跟别人协作 | ✅ 该 |
| 一次性的 / 无意义的会话 | 试个参数、问个问题、查个资料、纯粹闲聊 | ❌ 不该 |

⇒ 如果那些会话也认桌，它们会把办公室搞乱：

| 会乱在哪 | 具体会怎样 |
|---|---|
| 状态表会被垃圾淹没 | "认过桌的会话"里一半是"随便聊聊"、"测试 123" |
| 投递会投错 | 一张给"桌 03"的单子，落在一个只是路过的会话里 ⇒ 没人真的处理 |
| "这张桌在干什么"变得没法读 | 一个只开过一次的测试会话，"在干什么"这个问题没有意义 |

> ⚠️ **而"公告推送变成噪音"不在这张表里** ——
> **公告是广播，它不看认不认桌**：**没编号的会话照样收公告**（那是入口，见下面那段）。

### 所以"认桌"是一个准入机制

```
不认桌  ⇒  它就是一个普通的、独立的一次性会话（完全正常，不是二等公民）
认桌    ⇒  它主动加入了办公室：会收单子、会出现在状态表里
```

⇒ **认桌是"我要长期参与"的一个声明，不是自动发生的。**

⚠️ 而"收公告"不在这条线上 —— **公告是广播给所有会话的**（一次性会话、子代理都收得到），
认不认桌都一样。"认桌"在公告那条通道上不是准入，只是署名（见零点七）。

## 零点五、⭐ 为什么用编号而不是名字

| 用名字 | 用编号 |
|---|---|
| ❌ 会重名、会有近义名、会改名 | ✅ `01` / `02` 无歧义 |
| ❌ "投给环境维护桌" —— 哪一张？ | ✅ "投给桌 02" —— 地址明确 |
| ❌ 名字一改，所有引用全烂 | ✅ 编号是稳定的 |
| ❌ 得先知道别人叫什么 | ✅ 新会话不需要先认识谁，只需要一个号 |

而且编号让"名字"可以随便改：

```
桌号 = 01     ← 地址，稳定，不要动
桌名 = 前端   ← 给人看的，随便改（改了不影响投递）
```

⇒ **这是"地址"和"显示名"的经典分离** —— 而且它解决了一个实际问题：
你会想给桌改名（"后端"变成"API 服务"），但你不希望所有引用跟着烂。

### 一个顺带的巧合（⚠️ 但别拿它当判据）

我会话号的格式是 `session-<uuid>`，子代理的会不带这个前缀。
看起来能靠这个区分"桌会话"和"子代理" —— 但那是巧合，不是契约。

⇒ **真正的判据用平台自己标的血缘**：`parentSession`（有它 ⇒ 是子代理 ⇒ 不认桌）。

## 零点六、⭐ 认桌是怎么被邀请的（以及怎么"拒绝"）

要解决的问题：一个还没认桌的会话，该不该一直提醒它？

结论：

> ⚠️ **说清是谁在说**：
> **认不出桌时，插件往系统提示里放一句提议** —— 由**那个会话的 AI** 转达给你（*"要不要改成 `01-…`？"*），
> **你说同意它才用 `set_session_title` 改**；你不理会，它就**再也不提**。

机制（三道闸）：

| # | 闸 | 说明 |
|---|---|---|
| 1 | 只在"没认出桌"时才提 | 认出了（标题带 `NN-`）就永远不提 |
| 2 | **只提一次** | 记在存储里 ⇒ 用户不理会就不再唠叨 |
| 3 | 重启也不重提 | 因为那个"提过了"的记账是持久的，不是内存里的 |

⇒ 所以"拒绝认桌"的方式就是：什么都不做。
那个会话会安静地当一个普通会话 —— 不会有人来催它。

⚠️ 一个实现细节值得说：提议里会告诉 AI *"改不改由用户点头"* ——
**插件自己绝不会去改用户的标题**。AI 也只在用户同意后才调用改名工具。

为什么不用"自动改名"：标题是用户的东西。
一个会自动改你标题的插件，比一个偶尔提醒你的插件讨厌得多。

## 零点七、两个插件判"你是哪张桌"：判据一样了，用法还不一样


先说结论：**两个插件现在都从会话标题读桌号**（`NN-` 前缀）——
判据统一了：**两个插件都从标题读桌号。**
而它们拿这个身份做的事仍然不同：

| | `dsh-bulletin-dispatch`（投递） | `dsh-bulletin-announce`（公告） |
|---|---|---|
| 怎么知道你是谁 | ⭐ 标题的 `NN-` 前缀 —— 平台侧的事实 | ⭐ **也是标题，只有标题**（见下面那一节） |
| 认不出时回落到哪 | ⛔ **没有回落** —— 它还不是办公室成员（不记进状态表、收不到单子） | ⚠️ 回落 cwd 推导 → 再不行写"办公室"（署名而已，不影响谁收得到） |
| 它认的是什么 | 地址（"这活儿该送到哪张桌"） | 署名（"这条是谁发的"） |
| 认不出的后果 | 收不到单子（投递不认它） | 公告照样进它的上下文，只是署不上名 |

### ⚠️ 为什么"判据统一"这件事值得做（原来两边相反）

| | 原来 | 现在 |
|---|---|---|
| 投递 | 读标题 ⇒ 它认得出 | 读标题 |
| 公告 | AI 自己填 ⇒ ⚠️ 同一个会话，投递认得出、公告认不出 | 读标题 ⇒ 两边一致 |

⇒ 同一台机器上、同一个会话，两个插件对"它是谁"必须给同一个答案 ——
不然就会出现"单子送到了 03 桌，而它发的公告署着办公室"这种自相矛盾。

### ⚠️⚠️ **身份只认标题，不接受调用方自报**

**为什么会想"让调用方自报"**：听起来很合理 —— *"AI 读过办公室根 README，
按主题判断自己属于哪张桌时，它比标题更准。"*

**⚠️ 而它和上面那句是冲突的** ——
上面说"两个插件必须给同一个答案"，而"显式填就压过标题"**正好是在那个答案之外又开一个**：

| 场景 | 投递插件认为它是 | 公告插件署成 |
|---|---|---|
| 标题 `01-游戏开发` 的会话，填 `publisher: '02 桌'` | **01** | ⚠️ **02** |

**⇒ 那正是上面"自相矛盾"那句要防的事，只是换了个方向。**

**⭐ 所以**：**身份只认标题**（`NN-` 前缀），**`publisher` 参数留着但标了"已忽略"**
（留着参数，老提示里的调用就不会直接报错）。
**要代表别的桌发话，就让那张桌自己发**，或者写进正文（*"我替 02 桌转达"* —— **那读起来反而更诚实**）。

> ⚠️ **它有一条自测守着**：报错里出现"管理员是哪张桌"、或者署名跟着 `publisher` 走，测试都会红。

⚠️ 所以两句话仍然是错的，别照着说：

> ⛔ "认桌之后才会收到公告" —— 公告从来不筛桌（投递才筛）。
> ⛔ "公告的发布者一定是准确的" —— 标题读不到、又没人显式填时，它会写"办公室"；
> 那是诚实，不是准确。

## 一、四个地方、一条规矩

先说东西该放哪 —— 整套设计的地基就是这张表：

| 你想干的事 | 放哪 | 谁的 |
|---|---|---|
| 给自己干活 | 自己的工作目录 | 我的 |
| 给别人东西 | 对方的信箱（`00-通用\信箱\<对方>\`） | 它的（所有权当场转移） |
| 给所有人的东西 | 共享目录（`00-通用\`） | 办公室的 |
| 给用户的成品 | 交付区 | 用户的 |

这一条是整个设计的支点：

> "给别人东西"是**当场写进对方信箱**的 ——
> ⛔ 不要"写完放自己家、再叫对方来拿"（那正是"跨目录写"的来源）。

为什么这条能解决问题：老做法里，"交付"意味着别人要读写我的目录 ——
那是耦合，而且我一改名对方就烂。新做法把收件口挪到中立地带（共享目录里的信箱），
于是没人需要进别人家。

## 二、一轮协作的完整生命周期

```
① A 桌要请 B 桌做件事
     ├─ 简单（一句话 ＋ 指一个已经存在的地方）⇒ 直接发一张单子   ← ✅ 不要走信箱
     │        ⚠️ `ptr`（详见哪里）是必填的 —— 单子永远是指针型，
     │           没有"只在正文里把事说完"这回事（工具会直接拒掉）
     └─ 复杂（有附件 / 要留档 / 要来回）⇒ 写一份文件放进 B 的信箱，再发一张单子指向它
                                                    ▲
                                     ⭐ 信箱必须配单子（否则 B 不知道）
                                     ⭐ 单子不依赖信箱（指针指哪儿都行，不非得是信箱）

② B 桌某个会话先跑到 ⇒ 从系统提示里看到那张单子 ⇒ 取走
     └─ 取走后：同桌别的会话看不到它了（⇒ 同一轮里不会两个人都领到）

③ B 桌干完了
     ├─ 有产出 / 有分歧 ⇒ 写一份文件放进 A 的信箱 ＋ 发一张单子
     └─ 只是"处理完了，没有要给你的东西" ⇒ ⭐ 只发一张"已完成"单子
                                              （不要为了走流程造一份文件）
                                              ⚠️ 但 `ptr` 照样必填 —— 指原来那张单子/那份文档就行

④ A 桌收到 ⇒ 有实质内容就回到 ①；没有就停

⛔ 终止条件：双方确认没有什么需要再通知的 ⇒ 停止投递。
```

判断"要不要发这张单子"的唯一判据：

> **"对方看了，会做一件他本来不会做的事吗？"**
> 不会 ⇒ 不发。

不发这些（都是实践里总结出来的）：

| ⛔ 不发 | 为什么 |
|---|---|
| 收到 / 好的 / 已阅 / 感谢 | 那是回执 —— 而投递的语义明确是"不需要回执" |
| "你怎么还没做" | 投递不跟踪进度 |
| 为了把流程走完的空单子 | 循环就是这么来的 |

## 三、公告频道：为什么需要"记着见过什么"

天真的做法：开桌时把公告文件整个读一遍给模型看。

为什么不行：

| 问题 | 后果 |
|---|---|
| 公告只增不减 | 文件越来越长 ⇒ 迟早吃掉上下文 |
| 每次都说一遍 | 同一条说一百遍 ⇒ 噪音，模型开始忽略它 |

做法：给每个会话记一组 **"它见过哪些条目"的内容指纹**（`sha1(那一行)` 的前 16 位）。

⚠️ 不是"这个会话已经看到第几条了"：公告文件是各桌一起往末尾追加的，
行号会漂移 ⇒ 按"读到第几行"记，文件被编辑过一次就可能漏、也可能重。
而指纹认的是内容，不受这个影响。

```
开桌 → 读"见过的那些" → 推"没见过的" → 把推过的记进去
```

⇒ 于是"新条目"是一个可判定的状态，而不是"时间上比较近的那些"。

代码注释里那句话最准：

> **"游标代表『读者现在还记得什么』，不是『文件里发过什么』。"**

三个边角情况（都处理了）：

| 情况 | 行为 |
|---|---|
| `/mute` | ⭐ **只静音当前那个会话**：账冻住（不推进）⇒ 静音期间**仍在有效期内**的条目会在 `/unmute` 时补给你，而**一次最多展开 8 条**（超出只报数量） |
| 上下文压缩 | "见过的"随上下文一起没了 ⇒ **清空记账，下一步把"当前有效"的重发一遍**（不是"不重复"；重发时会说一句"这是上下文重建，不是新消息"） |
| 新会话 | 它什么都没见过 ⇒ 开桌时补看"仍在有效期内的"（不是"只看到以后新增的"） |

## 四、单子挂在"桌"上意味着什么

这是本项目最容易被误解的一点，所以说清它带来的四个后果：

### 1. 不重复干活（不需要锁）

```
两个会话同时跑到 ⇒ 谁先取走算谁的 ⇒ 另一个看不到它了
```

⇒ 比"分布式锁"简单得多，而且没有死锁、没有超时、没有"锁没释放"。

⚠️ 而它的保证范围要说清：

| 它保证 | 它不保证 |
|---|---|
| **同桌的两个会话不会在同一轮里都领到它** | ⛔ "已经取走的，重启后不会再被投一次" |
| —— | ⛔ 跨进程 / 跨独立 DSH 实例的唯一性 |

为什么："谁先取走"这件事**记在进程内的内存里**（一个 Map）；
而"取走"落库那一步是尽力而为的 —— 写失败时那条已经算被取走了，
但**重启之后它会重新变成待取**（源码里对这一点有明说）。

⇒ 所以准确的说法是：它避免的是"同一轮里两个人抢到同一张单"，不是"全局恰好一次"。
⚠️ 而这两种失败的样子差别很大：前者每天都会发生（所以必须挡），
后者只在崩溃/写失败时发生（所以知道就行，不值得为它引入一把锁）。

### 2. 会话结束/压缩/重开都不影响

单子是桌的，不是会话的。会话没了，桌还在 ⇒ 下一张单子照投。

### 3. 但不能往"某个会话"投单

如果你需要"这件事只给那个会话做"，单子做不到 —— 那不是它的设计目的。
（真需要的话，那是另一个问题：你要的是"指派给人"，不是"通知一张桌"。）

### 4. 也不能靠单子做"已完成"的账

**取走 ≠ 做完。** 想知道做完没有 ⇒ 那得有人去问（或者干脆别问，见根 README 的"不做"那节）。

还有一条最容易漏的：**单子只在"取走它的那一轮"可见**。

```
单子被取走的那一刻 → 出现在那个会话的系统提示里（就在取走的那一轮）
        ↓ 下一轮起
   连取走它的那个会话也看不到它了（同桌别的会话则从头到尾没见过）
```

⇒ 它是一条一次性的通知，不是待办清单。 想回看"这张单子后来怎么样了"，
只有状态表（`00-通用\投递状态.md`，插件生成的派生视图）——
`list_tickets` 只看**还没被取走的**，取走之后它也列不出来了。

## 五、派生视图：为什么状态表不让人改

| | 真相在哪 | 谁能写 |
|---|---|---|
| 公告文件 | 就在文件里（它是权威） | 各桌追加 · 用户可改可删 |
| 状态表 | 在插件的存储里 | **只有插件** —— 文件是它的投影 |

⇒ 所以状态表头上写着"不要手改，改了会被覆盖" —— 那不是偷懒，那是它的定义。

更硬的一条：别的插件也不许写它。
（我们的侧边栏面板能写公告，但明确禁止碰状态表 —— 因为它一写就成了第二个真相源。）

## 七、人来这一环

用户不是"另一个参与者"，规则不一样：

|       | 各桌（AI）   | 用户                |
| ----- | -------- | ----------------- |
| 发公告 | 可以提议 | 批准的人 |
| 改已有公告 | ❌ 只能追加   | ✅ 可以删改        |
| 收东西   | 走信箱  | 走交付区（那是"出件口"） |
| 静音    | —（静音是用户的命令） | `/mute`，只静音敲命令的那个会话 |

⇒ "只有用户能批准"这条不是技术限制，是设计 ——
公告是广播（会进每一个会话），所以它该有一个人在环上。

### ⚠️⚠️ 但"批准"是约定，不是闸门

一开始把这句写得太硬了（"唯一的批准者"、"唯一的写入口"）。实情是：

| #     | 写入口                         | 有没有技术闸门                                       |
| ----- | --------------------------- | --------------------------------------------- |
| 1 | 面板（`dsh-bulletin-panel`）  | ✅ 有 —— 发布前弹确认框 + 乐观锁                          |
| 2 | `announce` 工具（任何一张桌都能调） | ⚠️ 没有。它只在工具说明里写着"先征得用户同意"，**代码里没有拦截** |
| 3 | 直接改那个文件（用户、外部工具、Codex）  | ⚠️ 没有 —— 文件就是文件                               |

⇒ 所以准确的说法是：

> **"只有用户能批准"是一条约定**（各桌都该守），
> 而只有一个入口把它做成了结构（面板）。
>
> ⇒ 约定 + 一个结构化的入口，不是"唯一的闸门"。

为什么不做成技术拦截：拦不住。 第 3 个入口永远存在（那是个纯文本文件），
而给一个能被绕过的闸门，比承认"这是约定"更危险 ——
它会让人以为"没被拦住 = 被批准了"。

⇒ 我的选择是：把能结构化的那个入口结构化（面板），其余的照实说。
