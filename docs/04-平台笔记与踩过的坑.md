## 一、怎么"问平台"（比读文档可靠）

DSH 有一套检视器（Cordis Inspect），可以在运行时问出活的事实：

| 问什么 | 用什么 |
|---|---|
| 服务有哪些方法（精确签名 + 契约文字） | `Service.listService` |
| 事件有哪些、什么模式 | `Event.listEvents` |
| 某个插件"活的"配置 schema | `Config.listConfigs` |
| 这个会话能用哪些工具 | `Tool.listTools` |
| 前端有哪些插槽 + 主题 token | `Slots.listSubTree` / `Theme.listTokens` |

一条最有用的：`Config.listConfigs` 读的是加载器实际投影出来的 schema。

为什么这条重要：我们曾经装了新版本、日志也打了新版号，但那个键就是不生效 ——
用 `Config.listConfigs` 一读，活的 schema 里根本没有它（还是旧模块的）。
⇒ **"装上了"不等于"在跑"**。判据要用检视器读活的事实，不是看日志。

## 二、⚠️ `ctx.get` 在挂载那一刻取不到服务

症状：插件挂载时打出 `storageDomain=缺失`、`sessionQuery=缺失`……而且连续 7 次挂载都一样。

根因：`ctx.get` 在"插件刚挂载那一刻"拿不到任何服务。

正确做法：**用 `ctx.inject([...], (ctx) => …)`** —— 服务出现时回调才被调。

```js
ctx.effect(() => ctx.inject(['sessionPersistence'], (sctx) => {
  sctx.sessionPersistence.stat('…');   // ⭐ 在子 ctx 上，服务是「属性」
}));
```

两个附带的坑：

| # | 坑 |
|---|---|
| 1 | **子 ctx 上的服务是「属性」，不是 `ctx.get` 的结果** ⇒ 想兼容两种写法，就两处都试 |
| 2 | ⚠️ **在根 `ctx` 上不能点属性**：`ctx.sessionQuery` 会报 `cannot get property "sessionQuery" without inject` ⇒ 得用 `ctx.get('…')` |

> ⚠️ **这个例子只能是根 ctx，别写成 `agent.ctx`**：
> **`agent.ctx` 是「会话作用域」的子 ctx，不是根 ctx** ——
> 拿它举例，**正好把下面那条通用规矩讲反了**
> （子 ctx 上点属性**恰恰是可以的**，见上面那个 `sctx.sessionPersistence` 的例子）。
> **⇒ 例子和规矩必须指同一个 ctx，不然读的人只会更糊涂。**

通用规矩（⚠️ 但要看是哪个 ctx）：

| 在哪个 ctx 上 | 怎么拿服务 |
|---|---|
| 根 ctx（`apply(ctx, …)` 拿到的那个） | `ctx.get('…')` —— 别点属性（会抛 `without inject`） |
| `inject` 回调里的子 ctx | 服务就是属性（`sctx.sessionPersistence`）—— 正是上面那句示例 |

> ⚠️ 这两条曾经在本文里自相矛盾（示例用属性、下面的"通用规矩"说永远别点属性）——
> 因为当时没写清"指的是哪个 ctx"。规则要连适用范围一起写，不然就是一句会误导人的话。

⚠️ 验证条件：以上**两个组合都验过**（版本见本文开头那张表）——
DSH Desktop `0.10.0`（宿主 `@deepseek-ai/dsh-web` `0.1.7-rc.2`），
以及官方 DeepSeek Harness `0.2.0-rc.2`（宿主 `@deepseek-ai/dsh-web-app` `0.2.0-rc.2`）。
**别的版本没验过** —— 这些是平台行为，会变。

## 三、`ctx.setTimeout` 读一下就抛

症状：`ctx.setTimeout?.(…)` **静默跳过** —— 那一行像是"没这个服务就算了"，**而且一点声响都没有**。

实际：读 `ctx.timer` 会 `Error: cannot get property "timer" without inject`。

⚠️ **而"静默"不是 `?.` 干的**：

| 说法 | 对不对 |
|---|---|
| *"`?.` 把异常吞了"* | ⛔ **错** —— `?.` 只在**左边是 `null`/`undefined`** 时短路；**它不碰异常**（读一个禁读的属性会照抛） |
| ⭐ **当时真正吞掉它的是外层的 `catch`** | ✅ 那个 `catch` 本来是为别的事写的，**顺手把这一条也吞了** |

**⇒ 这条的教训比"要用 try/catch"更值钱**：
**"静默"通常不是某一行的错，是"某一层 catch 太宽"** ——
**宽 catch 会让"我以为它没被调用"和"它调用了但抛了"长得一模一样。**

做法：`try/catch` 包一层，失败就退回全局 `setTimeout`（**并在 catch 里留一行日志**）。

## 四、会话是追加的存储：**官方这版**能"创"、不能"删"

> ⚠️ 这一节讲的是**官方 `0.2.0-rc.2`**；**社区 `0.1.7-rc.2` 线是有删除的**，而且**真删文件** —— 差别就是下面这张表。

| 想做 | 官方 `0.2.0-rc.2` | 社区 `0.1.7-rc.2` |
|---|---|---|
| `sessionPersistence.list()` / `stat(id)` / `open(id)` | ✅ | ✅ |
| 删一个会话 | ❌ **没有 `delete`**（append-only 存储，契约如此） | ✅ `@Remote('delete') delete(...)`，摘要原文：*Permanently delete one ordinary Session **while retaining Workspace files*** |
| 存储层动不动文件 | ❌ 基类只剩一个**拒绝**用的壳：*this session persistence backend does not support deletion*；注释写着 *"**不删除会话文件** —— 日志在 `root` 下累积，**直到外部移除**；**seam 无删除接口**"* | ✅ JSONL 后端 `async delete(id)` **真的 `rm`** 掉那条会话日志（先拿写占用 + 目录租约，删完 sync 目录，Windows 跳过 fsync） |
| 界面入口 | ❌ 只有**归档**（`归档会话` ×11 · `archiveSession` ×200 · `永久删除` **0 处**） | ✅ 客户端 UI 有 `deleteSession()`（先放开主视图，等引用计数归零，再删） |
| 搜索索引 | —— | ✅ `_deleteSession("persisted" \| "live", id)` 清行 |

⚠️⚠️ **别被字符串骗了 —— 这张桌和 02 桌都差点栽在这儿。**

官方包里搜 `session_delete` 有 **16 处**、`deleteSession` **14 处**，看着像"有功能、只是没接 UI"。
**其实那是协议层留的一个可选 seam：**

```js
if (implementation.deleteSession) {
  app.onRequest(schema.AGENT_METHODS.session_delete, async (ctx) => (await implementation.deleteSession(ctx.params)) ?? {});
}
```

**"实现提供了才挂上"** —— 官方没提供。

**⇒ 判据是"问平台的活服务目录"，不是搜字符串：**

- `sessionController`（自称 *backing the generated `ctx.remote.session` namespace*）的 **22 个方法里没有 `delete`**；
- **91 个宿主服务里，名字带 delete 的只有 5 个** —— `credentials.deleteRecord` · `messageFeedback.delete` · `schedule.delete` · `workspaceController.delete` · `workspaceRegistry.delete`，**会话一个都没有**；
- 官方包里 `SessionDeleteRequest` / `SessionDeleteValue` / *Permanently delete one ordinary Session* **全是 0 处** ⇒ **不是藏起来，是这一版把类型定义都拿掉了。**

⇒ 所以"**插件删不了会话**"在官方这边不是写法问题，是平台没开这个口。
⛔ 而且**客户端插件也补不了**：面板（和任何客户端插件）只能调宿主**已经提供**的 Remote 方法 —— 加个按钮只会得到一个必然失败的按钮，那比没有更坏。
⇒ 另外界面也可能够不着：**子代理会话不列在侧栏，搜索也搜不到**（实测）。

⭐ **官方这边真要删怎么办（2026-10-03 补）**：宿主确实没这个口，但**"外部移除"这条路是通的** ——
生态里已经有插件做对了，例如 [`dsh-chat-manager`](https://github.com/WSL043/dsh-chat-manager)（第三方，MIT）：
它在侧边栏的会话菜单里给一个「永久删除」，守卫比"能删就行"细得多 ——
**文件名必须匹配** `^session(?:\.v[1-9]\d*)?\.jsonl(?:\.zstd)?$`、**跑着的会话拒绝**、
**两阶段隔离删除**（先挪走再删，中途失败能回滚）、删不干净**如实报告**，而且只碰**那一个会话目录**。
⇒ ⭐ **关键区别：它是宿主插件**（`apply(ctx)` 那一半跑在宿主里），所以能做到客户端插件做不到的事。

⚠️ 两个数据家的会话**是分开的**（官方 `~\.dsh\sessions`；社区壳时代 `%APPDATA%\dsh-desktop\harness\sessions`，**已停用**）——
社区那批只有在社区版里删得掉，官方这批用上面那个插件删。

⛔ **但"我们自己写一个删文件的工具"不做**：官方说日志会"积累到外部移除"，
可**平台怎么更新自己的名册 / 搜索索引没有契约**，最小安全集合（会话日志 + `session.lock` + `session_projcache` + 索引）
猜错的代价是"**不报错但状态是错的**"。要用就用别人已经验过、而且把守卫写全的那套。

`stat(id)` 的用法（实测过的语义）：

- 会话不存在 ⇒ 返回 `undefined`
- **它对"没在跑的旧会话"照样认得** ⇒ 可以安全地当"这个会话还在不在"的判据
- （我们验法：删掉一个会话，`list()` 少一个，而 `stat(被删的)` 从"有"变成 `undefined`）

## 五、会话日志是多帧 zstd

`zstdDecompressSync(buf)` **只解第一帧**。
真实的会话日志是几千个帧拼起来的（我们见过 ~6649 帧）。

⇒ 要按魔数 `28 b5 2f fd` 切开、逐帧解。

另一个现象：一个只有 header 的"空壳"会话，压缩后能有 300KB+，
解压后只有 270 字节。**别拿文件大小当"有多少内容"的判据。**

## 六、存储域：两个坑

| # | 坑 | 做法 |
|---|---|---|
| 1 | 版本号不是"随便加字段"就能升的 —— 把 `version` 从 1 升到 2 之后，所有写入都被后端拒绝（`StorageError: stored version 1 != expected 2`） | 加可选字段不是格式变更 ⇒ **保持 `version: 1`**，新字段用 `.default()` |
| 2 | ⚠️ 域被 dispose 之后，`enqueue` 会拒绝每一次写（`DomainError('closed')`），但 `table()` 仍然可用 ⇒ 拿"读得到"当存活判据是错的 | **探活要真的写一次** |

还有两条：

- `error.code === 'already-open'` ⇒ 复用（`facility.get(name)`），不要再建一个
- `defineDomain` 的名字/表名必须匹配 `/^[a-z][a-z0-9_]*$/`（不许有连字符）——
  而且它是在模块加载时校验的 ⇒ **名字写错会让 DSH 起不来**（我们真踩过）

## 七、`put` 返回的是 Promise ⇒ 同步 `try/catch` 抓不到它的拒绝

症状：两封真实的单子被静默丢掉了 —— 因为写失败被 `try { store.put(...) } catch {}` 吞了。

做法：`await` 它（或者用 `.catch`），**写失败必须让它冒出来**。

## 八、写文件：`Set-Content -Encoding UTF8` 会写 BOM

**BOM 会让 Harness 崩**（我们真踩过）。

⚠️ 但这条只对 Windows PowerShell（5.x）成立 —— 别把它推给所有版本：

| 哪个 | `-Encoding UTF8` 的行为 |
|---|---|
| Windows PowerShell 5.1 | ⚠️ **写 BOM** |
| PowerShell 6+（含 7.x） | ✅ **默认就是无 BOM**（`utf8NoBOM`） |

⇒ 所以准确的写法是：*"在 Windows PowerShell 上，`Set-Content -Encoding UTF8` 会写 BOM"*。
（当时用的是 5.1，没验过 7.x —— 而 7.x 上这句话是假的。）

⇒ 写文本文件一律用不带 BOM 的写法（Node 的 `writeFileSync(path, text, 'utf8')` 就是干净的）。

而且：要"覆盖一个文件"，**正确做法是「原子写」**：

```js
writeFileSync(tmp, text, 'utf8');
renameSync(tmp, path);        // ⭐ 同一分区上是原子的
```

为什么必须：如果直接往目标文件写、写到一半崩了 ⇒ 文件半截 ⇒
如果那个文件是别人依赖的（比如"各桌获取公告的唯一入口"）⇒ 那是事故。
`rename` 保证读者**要么看到旧全文、要么看到新全文**。

### ⚠️ 而"追加"**不在这条规矩的管辖范围**

**这条规矩管的是"覆盖"** —— 而**追加是另一回事**：

| 动作 | 会不会写出半截文件 | 该怎么做 |
|---|---|---|
| **追加**（`appendFileSync` / `O_APPEND`） | ❌ **不会** —— 内核保证一次 `write` 落在文件末尾；崩了也不会留半行 | **`appendFileSync` 就行** |
| **覆盖**（`writeFileSync` 直接写） | ✅ **会** | **临时文件 + `rename`** |

**⭐ 而我们仓库里两种都出现过，而且都对**：
**公告插件往 `公告.md` 追一条 ⇒ 用 `appendFileSync`**（纯追加）；
**面板写删除记录 ⇒ 读全文 → 拼一行 → 原子写回**（⚠️ **它不是纯追加** —— 文件头要按需补，所以是"读改写"）。

**⇒ 一句话**：**不是"追加不能用 `appendFileSync`"，而是"那次这个动作不是纯追加"。**
（⚠️ **别把理由说成"`appendFileSync` 不是原子的"** —— 追加恰恰是原子的。）

## 十、插件生态的两条事实（选依赖时要知道）

| 事实 | 说明 |
|---|---|
| `dsh-better-sidebar` 是一个"服务化"的侧边栏框架 | 它把 `ctx.betterSidebar.registerTab` 开放给所有插件，它自己的 5 个内置页走同一套 API ⇒ 这是一条稳定的扩展缝 |
| ⚠️ 很多插件直接 import `@deepseek-ai/dsh-client-ui-primitives` | 那是**内部包**，会无声变化。**一个抛错的组件会把整个插槽条目变成空白**（控制台 `slot entry crashed`）。更稳的做法是自己写控件 + 只用主题 token |

前端插件的最小形态（不需要构建工具）：

```js
window.__ModuleLoader__.load({
  id: 'your-package-name',
  factory(require) {
    const React = require('react');        // ⭐ React 从浏览器模块表里拿
    const h = React.createElement;
    /**
     * ⚠️ **注入 `betterSidebar`，不是 `slots`**（写成 `slots` 而下面用 `ctx.betterSidebar`
     * ⇒ **在"点属性"那一刻就抛**）。
     *
     * ⭐ **判据**：`inject` 里列的，必须**正好是你接下来要用的那些服务** ——
     * 列少了会抛，列多了会白等一个用不上的服务。
     * （我们自己的面板就只注入这一个：`inject: ['betterSidebar']`。）
     */
    return { inject: ['betterSidebar'], apply(ctx) { /* ctx.betterSidebar.registerTab(…) */ } };
  },
});
```

样式用主题 token（`--dsw-alias-*`）⇒ 亮色/暗色/换肤自动跟着变，不用写两套。
