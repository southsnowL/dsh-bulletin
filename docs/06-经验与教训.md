# 经验与教训：几次代价较大的误判，和三条走不通的路

> 这份是给自己看的（也给下一个做同类东西的人）。
>
> 上面几份文档都在讲"开发时想明白了什么"。这份讲"开发时想错了什么" ——
> 而且我尽量把当时真的以为自己对的那个状态写下来，因为那才是有用的部分。

---

## 零、⭐ 先给结论：这几次失败有一个共同点

我把下面这些事排了一遍，发现疼的那几次全是同一种：

> 它们都不报错。
> 它们只是不工作 —— 而且**看起来像在工作**。

| 那次失败 | 它报错了吗 | 它看起来像什么 |
|---|---|---|
| 挂载时取不到服务 | ❌ 不报错 | 日志说"存储域未就绪"，功能照常装配了 |
| 存储域版本号写错 | ✅ 报错（但被吞了） | 写入静默失败 |
| `put` 的 Promise 拒绝被吞 | ❌ 完全不报 | 两封真实的单子凭空消失 |
| 自己的"见过活着"集合 | ❌ 不报错 | 回收看起来在跑（日志每轮都说"没有发现已消失的会话"） |
| 状态表早写 9 毫秒 | ❌ 不报错 | 仪表盘少一行，看起来"就是那样" |
| 死配置键 | ❌ 不报错 | 读配置的人以为单子存在那个文件里 |
| 一句挂载日志说错了 | ❌ 不报错 | 误导了我自己一整天 |
| 面板写的公告少两段 | ❌ 不报错 | 面板显示得好好的，各桌永远收不到 |
| 诊断工具调了不存在的函数 | ✅ 报错（但那两个工具没人常调） | 一点就崩 —— 而"没人用"让它活了很久 |
| ⭐ 拿真文件名当测试样本（见二.5） | ❌ 不报错 | 删的那一刻什么都没发生 —— 要等下次跑测试才看见 |
| ⭐ 替换字符串多带了一段（见二.6） | ❌ 不报错 | 少了一整节，而剩下的读起来依然通顺 |
| ⭐⭐⭐ 前端一个"清洗"函数把新字段扔了（见二.7） | ❌ 不报错 | 界面上永远显示 0，而接口返回的数字是对的 ——<br>于是我去查后端，每轮都真修掉一个 bug，而界面一直没变 |

⇒ 真正的教训不是"某某 API 有坑"，而是：

> **一个静默的失败，比一个崩溃危险得多。**
> 崩溃会逼你去看；静默会让你以为自己是对的。

而**上面那张表最后三行**（⭐ 标记的那三条 —— 也就是**后面「二、另外八条教训」里的第 5、6、7 条**）还各多一层：

| 条目 | 那一层 |
|---|---|
| **二.5 / 二.6** | 不是别人坑我，是我自己坑自己 —— 都是"一个动作做了两件事，而我只打算做一件" |
| **二.7** | 我有四个症状，却当成四件事一件一件查 —— 而其中两个（"星号修好了""标记显示了"）本来能一句话排除整条路线 |

**⚠️ 编号必须带上"它在哪一节里"**：上面那张表有 12 行，
只写"5、6、7"会让人**去数那张表的第 5/6/7 行** —— 那是别的三件事。

7 那一层的判据：

> 症状越多、越像彼此独立的，就越该先去找"**能同时解释它们的那个原因**"。
> 别一个一个查。
>
> ⚠️ 而它当时的样子很具体：我为"界面上那个数字是 0"这一件事，
> 在 45 分钟里发了 8 个版本 —— 而每一版我都"有个理由认为这次对了"。
> ⇒ "久"不是重点，"每一版都以为自己对了"才是。

而 5 / 6 那一层的判据：

> 不是"我小心一点"，是"让那个动作不可能做第二件事"：
> **样本造在临时目录里** · **替换字符串要短到不可能多带**。

⇒ 所以本项目后来形成了三条硬习惯（见第四节）。

## 一、当时四次真的以为自己是对的


### 误判一："同一行日志，两个插件给出不同答案" —— `ctx.get` 在挂载时不可靠

当时的处境：热重载之后，连续 7 次挂载，每次都退回兜底的文件存储：

```
已挂载 v0.2.3 → 存储域未就绪 —— 状态走兜底文件 → 功能已装配 ×4
```

⚠️ 而同一个进程里，另一个插件（公告）却报 `storageDomain=可用`。
同一个 API、同一个时刻、两个答案。

当时以为：*"大概是我这个插件装配得早了一点。"* ——
于是试着延迟、试着重试 —— 都没用。

转机是"让日志说清楚"，不是推理。我在那句"未就绪"里加了个探针，输出是决定性的：

```
probe: storageDomain=无 storage=无 sessionQuery=无
```

⚠️ 决定性的不是"storageDomain 无"，而是"连我确认能用的 `sessionQuery` 也是无"。

⇒ `ctx.get` 在"**插件刚挂载那一刻**"，什么都取不到（那些服务是之后才挂上去的）。

根因：契约里早就写着答案 ——

```
hardDependency: { inject: ['storageDomain'] }
```

`inject` 的语义就是"让框架保证依赖可用之后再叫我"。
而我用了 `ctx.get`（"现在有什么我就拿什么"）—— 在挂载那一刻，答案是"什么都没有"。

⇒ 修法：`ctx.inject(['storageDomain'], (sctx) => …)`。

这次误判真正的价值：它同时解释了一天前的一次误判
（那次报"`storageDomain` 缺失"，当时靠"懒打开"绕过去了，以为解决了 ——
其实根因就是"查得太早"，我绕过了症状，没碰到病根）。

而更值得记的是这个：

> 那句"存储域未就绪"的挂载日志，是我自己写的。
> 它写出来之后，我每次看到它都以为那是真的 —— 一连 7 次。
> ⇒ **一条说错的日志，会误导写它的人。**

顺带把开头那个疑问收掉：

开头写的是"同一个 API、同一个时刻，两个答案" —— ⚠️ 而"同一个时刻"这个前提就是错的。

| 谁 | 那一次 `ctx.get` 发生在什么时候 | 读到什么 |
|---|---|---|
| 公告插件 | 懒取 —— 它真正用到存储域的那一处，是到"要写游标"的时候才读的（`getDomain()`） | 可用（那时服务早挂回来了） |
| 本插件 | `apply()` 里，也就是挂载那一刻 | 什么都没有 |

⚠️ 而且热重载里两个插件本来也不是同一刻挂载的（一个接一个）。
⇒ `ctx.get` 回答的是"此刻" —— 把两次不同时刻的采样当成"同一时刻的两个答案"，
这个矛盾是我自己造出来的。

⇒ 而声明了依赖的一方根本看不到这个假象：`inject`
（`hardDependency: { inject: [...] }`，或 `ctx.inject([...], cb)`）的语义就是
"框架保证依赖可用之后再叫我" —— 它根本不会被叫在"服务还没就位"的那一刻。

### 误判二：为了防误删，造了一个"重启后永远不工作"的东西

当时的处境：用户问 *"我把一个会话删掉，系统和仪表盘能不能也同步删掉？"*

我做了一版：定时问平台"这个会话还在吗"（`stat`），不在就清掉记录。
但为了防误删，我加了一道自认为聪明的闸：

```
只有"曾经查到过它活着"的会话，才敢删。
```

它看起来完美 —— 平台一时查不到，也不会误删。

然后用户实测：删掉一个会话，回收跑了 4 次都没清它，
而日志每轮都说 *"没有发现已消失的会话"*。

逐条打印才看清：

```
那个会话 → stat 返回 undefined（平台说它不存在）
但它在"见过活着"的集合里：没有
⇒ 代码在这里静默跳过
```

根因：进程重启过 ⇒ 那个集合是空的 ⇒
那个会话从来没在这个进程里被"认领"过 ⇒ 安全阀永久拦着它。

⇒ 为了防误删，造了一个"重启后就永远不工作"的机制 —— 而且它一声不响。

修法不是"把那个集合持久化"（我一开始真的准备这么修，那是在给一个不该存在的东西续命），
而是去仓库里找平台有没有现成的：

```
sessionQuery.listSessions()   ← 契约："the complete logical corpus"
```

⇒ 拿它当**权威名单**。不需要内存集合、不需要持久化、跨重启天然正确。

⭐⭐ 这次误判里，最值得记的地方：

> 这个插件的职责是"清理不一致" —— 而我在里面亲手造了一个新的不一致
> （一份会跟真相脱节的、我自己的副本）。
>
> 这正是这个项目一直在修的那类 bug —— 差点把它请进门。

⚠️ 而它和本项目那条规矩直接冲突：

> 同一件事存两份，才是病根。
> 我那个"见过活着"的集合，就是一份**多余的副本**。

### 误判三："数出来的数，不等于实际数"（同一天犯了三次）

这一条单独列出来，因为它不是技术问题，是一种思维方式上的毛病。

| # | 我以为 | 实际 | 差在哪 |
|---|---|---|---|
| 1 | 某段引用有 177 处（用了"行匹配数"当"出现次数"） | 117 处 / 23 个文件 | 指标口径不同，我却拿来当同一个数用 |
| 2 | "跨桌写在上线之后归零了" | 那几小时只有两张桌在跑 ⇒ 这个"零"根本没机会发生 | 把"没发生"当成了"没出现" |
| 3 | 状态表"表头写 5、只有 4 行" ⇒ 报成产品 bug | 是我自己的检查脚本粗 —— 它匹配不到"办公室"那一行 | 我的观测方式覆盖不全 |

⇒ 三次都是同一个形状：

> 拿"数出来的"当"事实"，而没有先问一句"**这个数法覆盖全了吗？**"

后来的做法：报任何数字之前，先问三句 ——

1. 这个数的口径是什么？（行？出现次数？文件？）
2. 我的观测方式覆盖了全部情况吗？（有没有我匹配不到的类别？）
3. 这个"零"，是"真的没有"，还是"没机会发生"？

### 误判四：⭐⭐ "两个值相等"不等于"它们同源"（上述那批错误的最强版本）

背景：用户报"投递那里，取走的会话和投单的会话是一样的"。

我给出的诊断（写进了一份给前端的 bug 报告）：

> *"规律完全对上：前端显示的是 `source`（发起方）……
> ⇒ 桌号取自 `source`，会话名取自 `takenBy`。"*

它为什么看起来那么硬：截图上的值 恰好等于 `source`（04 和 03 完全对应）。
两个数值一模一样 —— 还能有错？

错在哪：我没验那两个值是不是从同一个地方来的。

真相：面板手里根本没有 `source` —— 状态表里就没那一列。
它不可能把 `source` 显示成取走方。我看到的 `04`，是别的东西恰好也是 04
（同一张桌的名字，出现在两个不同的位置上）。

而真正的 bug 是两处显示决定叠在一起：

| # | 真问题 |
|---|---|
| 1 | 卡片标题显示"单子投给哪张桌"，但没写明（没有动词）⇒ 看起来像"谁投的" |
| 2 | "取走的会话"和标题是同一张桌时，它把桌号省了、只留会话名 ⇒ 标题 `03 本机维护` 与下面那行 `本机维护` 摆在一起，看起来就是同一张桌 |

⇒ 数据从头到尾都是对的。是"显示方式"制造了一个不存在的矛盾。

⭐⭐ 这次误判最值钱的地方：

> 接手的人信了我的错结论。
> 它照着我说的"去查 `source`"查了一轮，才发现面板压根拿不到 `source`。
>
> ⇒ 一个"错得很硬"的结论，比一个含糊的结论危险得多 —— 因为它会被相信。

教训：

| # | |
|---|---|
| 1 | "两个值相等"≠"它们同源"。先问"这两个数是从哪来的"，再下结论。 |
| 2 | ⛔ **别把猜测写成"查明"** —— 我写的 *"规律完全对上"* 那语气像是验证过了 |
| 3 | "数据对不对"和"看起来对不对"是两件事 —— 数据全对，界面照样能让用户误读 |
| 4 | ✅ "看起来一样"这种报告是有效的 —— 他没说"字段取错了"，他说的是现象，而现象是真的 |
| 5 | 错误的诊断要留在档里（那份 bug 报告我改成了"误诊复盘"、没删）—— 否则下一个人会再踩一遍 |

## 二、另外八条教训

> ⚠️ 这一节是一张表，不是一篇过程记录 ——
> **每一条只留"读者能用的那一句"**（过程见「一、那几次误判」那几节）。

| # | 发生了什么 | 教训 |
|---|---|---|
| 1 | 领域名里用了连字符（`bulletin-announce`），而平台要求 `/^[a-z][a-z0-9_]*$/`。它在模块加载时校验 ⇒ 不是插件坏，是 DSH 起不来。 | 平台的命名约束要**在"起名字之前"看**。（当时我甚至不知道该看哪个文档 —— 是报错信息救的。） |
| 2 | `put()` 返回 Promise，我用同步的 `try/catch` 包它 ⇒ 拒绝被吞掉。发生了两次，直到"应该有单子但没有"。 | 任何返回 Promise 的写操作，不 `await` 就等于没写。<br>而且**写失败必须能冒出来** —— 一个吞掉写错的存储层，比一个会崩的存储层危险。 |
| 3 | 加了一个可选字段就升了协议版本号 ⇒ 后端拿旧 version 一比 ⇒ 所有写入被拒绝。 | "格式变更"指的是"**旧读者还能不能读**"。 加可选字段旧读者照样能读 ⇒ 不是格式变更。 |
| 4 | 我自己的检查脚本骗了我三次：一条断言守着错的写法；汇总脚本只累加"通过数"、没检查"0 失败"；搜"不许 import 某某包"匹配到我自己注释里那句话。 | ⭐ **检查脚本本身也要被检查。**<br>（现在的做法：判据要落在真实代码上，不落在"提到它的文字"上 —— 先剥注释再查。） |
| 5 | ⭐⭐ 做验证的时候把一个真文件删了 —— 我拿一个真实的文件名当"测试样本名"。 | ⭐⭐ **样本要造在临时目录里**，别拿真文件当样本。<br>⇒ 判据：任何"删除 / 覆盖"的动作，先问"这个路径是谁的"。 |
| 6 | ⭐ 改文档时用一次替换删掉了整整一节 —— 替换字符串多带了一段，而剩下的读起来依然通顺。 | ⭐ 替换字符串要短到不可能多带；<br>**改完要回头数一遍小节。**<br>⚠️ 而这一条我自己又犯过一次（就在改这一节的时候）—— 所以它现在是用"行号 + 自检"做的。 |
| 7 | ⭐⭐⭐ 查了三轮后端，而真凶在前端一个"清洗"函数里：后端新加的字段被 `normalizeData()` 这个白名单安静地扔掉了。 | ⭐ "清洗 / 归一化"这类函数是隐蔽的白名单 —— 它不报错，只是把新字段扔掉。<br>⇒ 别用白名单：**透传 + 只补默认值**。<br>⭐⭐ 症状越多、越像独立的，就越该先找"能同时解释它们的那个原因"。 |
| 8 | ⭐⭐⭐ 一个语法错，我用五种方法都没定位到 —— 而其中一次是我的诊断脚本自己坏了（我在脚本里嵌了被诊断的正则，转义被吃掉）。 | ⭐⭐ 诊断脚本里**不要嵌"被诊断的语法"** —— 用文件拼文件，别经过字符串字面量。否则你修的是探针，不是问题。<br>⭐ `node --check` 报的行号会偏；`grep` 报的不会。<br>⭐⭐⭐ **"删掉重写"是合法选项**：那函数只有 5 行，重写 10 秒 —— 别陷在沉没成本里。 |

第 7、8 条那一层的共同点：

> 它们不是"我犯了个错"，是"我的方法有缺陷" —— 那比单个错误更值得看。

## 三、⚠️ 三条走不通的路（试过，然后放弃了）

这些比"成功的经验"更值钱，因为它们看着都很合理。

### 走不通之一：做"越权写检测"

想法：如果某个会话改了不属于自己的目录，拦下来。

为什么走不通：判据根本分不清。

| 情况 | 该拦吗 |
|---|---|
| 改自己的文件 | ❌ 不该 |
| 把委托书写进对方的信箱 | ❌ 不该 —— 那正是正确做法 |
| 把成果写进交付区 | ❌ 不该 |
| 跑进别人的工作目录乱改 | ✅ 该 |
| 改共享目录里的公共文件 | ⚠️ 可能对、可能错 |

⇒ 光靠路径，"许可的交付"和"越权改动"长得一模一样。

而且更根本：**边界最终是靠约定维持的** ——
一个基于路径的护栏，既拦不住真心想绕的，又会误伤正确操作。

⇒ 真正的解法不是"检测"，是"取消那个动作存在的必要"：
把收件口挪到中立地带（信箱）⇒ "进别人家"这件事从流程上不再需要发生。

⇒ 这就是为什么我的文档里写的是：治因，不治症。

### 走不通之二：做"自动扫副本 / 自动巡检派单"

想法：维护一份"办公室事实"，扫全盘找出与它不符的副本；
定期体检，发现问题自动投单给相关的桌。

为什么走不通：假阳性是结构性的，不是调参能解决的。

> 任何一份事实，都会有正当的副本：摘录、引用、翻译、历史版本、测试夹具……
> **"和权威不一致"不等于"错了"。**

⚠️ 实测：有一次体检报告列了"10 处问题"，其中 6 处是假阳性。
⇒ 自动派单会把 6 条噪音投出去 —— 而收到噪音的人，很快就不看单子了。

而且它会自我循环：
A 巡检发现 B 的问题 ⇒ 投单 ⇒ B 修 ⇒ B 巡检发现 A 的问题 ⇒ ……

⇒ 保留的形态：体检报告是一份文档，各桌自己去读自己那一节。
"要不要告诉那张桌"这一步，**留给人（AI）判断**。

⇒ 一条推广的判断：

> "检测异常"可以自动算，
> "要不要因此打扰别人"不能 —— 后者需要判断力。

### 走不通之三：做"万能配置"（这条最根本）

想法：把"桌号、目录名、公告格式"都做成配置项 ⇒ 谁都能用。

为什么走不通：

> ⚠️ 第一个理由（"要布环境 ⇒ 不可能通用"）我们后来自己驳掉了 ——
> "要布环境"说的是"麻烦"，不是"不可能"：麻烦只影响愿不愿意装，不影响它能不能被抽象。
> ⇒ 完整的辨析见 [`01`](01-思路.md) **第七节「这套东西不适合什么」**。

而真正站得住的理由是这一条：

> "桌"这个概念是一个约定。
> 把它抽象成"一个随便填的字段"，它就从"我们的规矩"退化成"一个字段" ——
> 好处跟着约定一起消失。

⇒ 所以现在的决定是：先把这一版公开出来，暂不扩成通用配置系统 ——
那是**我们的选择**，不是"技术上做不到"。

| 做什么 | 不做什么 |
|---|---|
| 把思路和机制公开（`docs/01` 就是干这个的） | ❌ 不做"万能配置" |
| 公开"我们这一版"，把前提写在最前面 | ❌ 不假装它通用 |

而这条有一个正面的版本（我认为它是这份文档里最有用的一句）：

> **把前提说清楚，比假装通用更诚实，也更好用。**

## 四、⭐ 于是形成了三条开发的硬习惯

都是从上面这些误判里长出来的。

> ⚠️ 前两条来自"平台坑我"，第三条来自"我自己坑我自己"（二.5 / 二.6）——
> 而且第三条是最难改的，因为它没有外部原因可以怪。

### 习惯一：能问平台，就别自己记

| | |
|---|---|
| ❌ 自己记 | 你维护了一份会跟真相脱节的副本 —— 而且它失效的时候不会报错（见误判二） |
| ✅ 问平台 | 平台知道真相，你不需要知道 |

具体做法：

| 想知道的 | 问谁 |
|---|---|
| 现在有哪些会话？ | `sessionQuery.listSessions()`（权威名单） |
| 这个会话还在吗？ | `sessionPersistence.stat(id)`（返回 `undefined` = 不存在） |
| 这个插件活的配置 schema 长什么样？ | 平台的 Config 检视器（不是看日志） |
| 平台有没有某个服务？ | 服务契约（不是"我挂载时取到没取到"） |

这条的推论："我读到了什么"不是事实，"平台说什么"才是事实。
（误判一里那句误导我的日志，就是"我以为我读到的就是真的"。）

### 习惯二：静默的失败最危险 —— 所以凡是"跳过"，都要留痕

这一条是从误判二和误判三直接来的。

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| ⭐ **拿不到平台的权威名单** | 按"我自己的判断"硬删 | **一条都不删**，并说清"拿不到名单，这一轮没动任何记录" |
| ⚠️ **一个删不掉的东西** | 当作删了 | 报出来："这几个没删掉"（`skipped`） |
| 一段解析不了的内容 | 丢掉 | 报出来："有 N 行看着像公告却解析不了" |
| 配置里有不认识的行 | 忽略 | 如实说明 |
| 没被调度的定时任务 | 什么都不打 | 打一行（否则你分不清"没被调用"和"调用了但判定不用做"） |

> ⚠️ **"不敢做"也要留痕** —— 不然你分不清"它确实不该删"和"我的判据坏了"。
> （那条"见过活着"的安全阀就是这么坏的：判据是"**我见过它活着吗**"，
> 而**进程一重启那个集合就空了** ⇒ **重启前删掉的会话永远清不掉**。）

一句话：

> 静默的防护，看起来像坏了。
> 而"看起来坏了"会让你去查一个根本不存在的问题 ——
> 当时真的为那个"回收不工作"查了很久（那次就是误判二）。

⚠️ 但别把两件事混成一件：

| | 误判二那次 | 这条规矩说的是 |
|---|---|---|
| 它到底有没有在工作 | ❌ 没有 —— 安全阀静默跳过（那个会话在 `sessions` 表里，却永远过不了"我见过它活着"这一关） | ✅ 在工作 —— 只是有理由地决定不删（比如这一轮拿不到平台名单） |
| 你查得出来原因吗 | ❌ 查不出来 —— 只能逐条打印才看清（日志每轮都说"没有发现已消失的会话"） | ✅ 查得出来 —— 那一轮会明说"这一轮不删任何东西" |

⇒ 所以"静默地不删"和"有理由地不删"是两件事 —— 区别不在删不删，**在有没有留痕**。
⇒ 这两件事正好被这条规矩分开了：误判二修掉了前一种，而这一条防的是"后一种又变回前一种"。

### 习惯三：⭐ 一个动作，只许做一件事

这一条是从二.5 和二.6 来的 —— 而那两次的肇事者是我，不是平台。

两次的形状完全一样：

| 我打算做的 | 实际做的 | 结果 |
|---|---|---|
| 删掉几个测试样本 | 删掉样本 和 一个真文件 | 仓库缺了个文件，当时什么都没发生 |
| 替换 Agent Teams 那一节 | 替换它 和 删掉后面一整节 | README 少了"文档"入口，剩下的读起来依然通顺 |

⇒ 所以判据不是"下次小心一点"（那是决心，不是方法），是**让那个动作不可能做第二件事**：

| 做法 | 为什么它管用 |
|---|---|
| 样本造在临时目录里，名字也带 `.probe` 之类 | 物理上碰不到真文件（比"我记住别删它"可靠） |
| 替换字符串短到不可能多带 | 多带一段是我那次唯一的错因，短就没有这个错因 |
| 大段改动之后，立刻数一遍结构（小节数 / 行数 / 链接数） | 让"删多了"在几秒内暴露，而不是等上线 |

一句话：

> **"我会小心"不是一道防线，是一个愿望。**
> 防线是"让那个错误没法发生" —— 临时目录、短字符串、改完就数。

## 五、如果只记一句

>
> ⇒ 所以：**能问平台就别自己记；凡是跳过就留痕；一个动作只许做一件事。**
