# 可视化面板

> 可视化不是这个项目的重点 —— 重点是那几个协作机制（见 [`01`](01-思路.md)）。
> 面板只是把那些机制显示出来给人看的一层皮。
>
> ⇒ 所以这里只说三件事：
> ① 做了什么 ② 边界在哪 ③ 想改前端的话，几件必须知道的事。
>
> 至于好不好看，各人都有各人的品味，你可以尽情的改。

---

## 一、做了什么

DSH 的右侧栏可以放插件注册的卡片页 ——「办公室」：

```
┌─ 办公室 ────────────────────────────────┐
│  [logo] 办公室          [只看新] [刷新]  │
│  公告与跨桌投递                          │
│  ┌────┐ ┌────┐ ┌────┐                   │
│  │ 6  │ │ 0  │ │ 4  │   ← 点数字跳分栏   │
│  │公告│ │待取│ │会话│                   │
│  └────┘ └────┘ └────┘                   │
│  公告  投递  健康                        │
│  ─────────────────────────────────────  │
│  [02] 环境维护 · 09-30          长期      │
│  跨方往来改走「信箱」：…                 │
│  详见：README-信箱怎么用.md    [编辑]    │
└──────────────────────────────────────────┘
```

它解决的是一个很具体的不适：

> 公告是一个纯文本文件、投递状态是另一个纯文本文件 —— 想看它们得去翻文件。
> 而"办公室正在发生什么"，人其实想一眼看到。

三个分栏：

| 分栏 | 显示什么 |
|---|---|
| 公告 | 条目列表（发布者 / 日期 / 有效期 / 一句话 / 详见） |
| 投递 | 「待取 / 已取走」两张表 |
| 健康 | 面板版本 / 存储 / 落盘确认 / 删除记录 / 文件路径 |

### 它具体能干什么

① 读：三个分栏 + 几个小动作

| #     | 功能            | 说明                                   |
| ----- | ------------- | ------------------------------------ |
| 1 | 顶栏三个数字    | 公告 / 待取单子 / 认过桌的会话 —— 点一下就跳到对应分栏 |
| 2 | 分栏带数量     | 页签上直接写着有几条                           |
| 3 | 方向键切分栏 | 不用鼠标（`←` `→`） |
| 4 | 搜索 | 搜表格、单号或正文；搜索时收起的分节上也会写"N 条匹配" |
| 5 | 按发布者筛     | 只留某张桌发的                              |
| 6 | 「只看新」开关 | 只显示"你还没看过"的条目。<br>⚠️ **这里的"新"和「见过数」不是一回事**：见下面那一节 |

#### ⚠️ 两个"新"别搞混（**一个在浏览器里，一个在插件里**）

| | **「只看新」的"新"** | **「见过数」的"见过"** |
|---|---|---|
| **谁记的** | ⚠️ **面板自己在浏览器里记的**（一个"条数基线"） | 公告插件记的（**每个会话一份**） |
| **怎么算** | 你**离开这个分栏**时记下条数；回来时，**在这之后新增的**就标成「新」 | 那个会话的"见过"记录里有没有这条 |
| **刷新页面** | ⚠️ **重置**（基线跟着当前条数走 ⇒ 全都不是"新"了） | ❌ 不受影响（那在插件的存储里） |
| **它是给谁看的** | **你自己** —— *"我离开这会儿，来了什么"* | **所有会话** —— *"这条有多少人看过"* |

**⇒ 一句话**：**「只看新」是"你的视线离开期间发生了什么"，和"哪个会话见过它"是两码事。**
⚠️ **别把面板这个"新"当成"我还没读过"的证据** —— 它连刷新都活不过。

② 写的部分（只有用户能用）

| # | 功能 | 说明 |
|---|---|---|
| 7 | ⭐ 发布公告 | 写在界面上，不用去改文件 |
| 8 | 有效期有快捷选项 | 常用天数一点就有，也能自己填 |
| 9 | ⭐ 边写边看 markdown 预览 | 正文里有 markdown 时实时渲染 |
| 10 | ⭐ 编辑已有公告：先看"改前 / 改后"对照 | 确认了才保存 |
| 11 | ⭐ 草稿不丢 | 写接口没上线 / 出错时，你写的东西还在 |
| 12 | ⭐⭐ 文件被别处改过 ⇒ **提示你刷新，不偷偷重试** | 两道乐观锁之一：文件指纹对不上就拒绝，绝不猜"大概是想改那条吧" |
| 13 | ⭐ 删除公告（见 §三） | 藏得深、要过一次确认框、删之前告诉你几个会话见过它；删完的记录在「健康」页画成一条时间线 |
| 14 | ⭐ 公告搜不到时会说"它可能被删了" | 并带着搜索词跳到删除记录（见 §三） |
| 15 | ⭐ 每条公告上直接显示"几个会话见过" | 不用点进删除框才看得到（见 §三） |

③ 排版：窄 / 中 / 宽三档

| 面板宽度 | 变成什么样 |
|---|---|
| ≥ 900 px | 两列（卡片并排放）+ 边距放宽 |
| 420 ~ 900 px（默认） | 单列 |
| ≤ 420 px | 紧凑：边距收窄、统计数字变小、副标题和 logo 隐藏 |

> ⚠️ 实现上有个细节值得说：宽度是用 `ResizeObserver` 量出来的，
> 面板自己不给根节点加尺寸约束 —— 所以侧栏自己拉伸就行，卡片不用管外面多宽。

④ 细节（都是"用起来才知道要有"的）

| # | |
|---|---|
| 14 | 每个分栏记住你滚到哪 —— 切走再切回来还在原处 |
| 15 | 投递页默认显示"待取"；没有待取的就显示"已取走"（不给你看空表） |
| 16 | 长正文真的放不下才出现「展开」 —— 不是写死截断几行 |
| 17 | 健康页的文件路径可一键复制 |
| 18 | 窗口最小化时暂停刷新（不白耗） |
| 19 | 尊重系统的"减少动态效果"偏好 |
| 20 | 只读时藏起发布/编辑按钮（`allowWrite: false` 时） |
| 21 | 一条公告出错不会让整张卡片变空白 —— 有错误边界兜着 |
| 22 | 删除失败时说清"能不能确定" —— 见 §三 |

⇒ 一句话：它把两个纯文本文件变成了"能读、能搜、能写、还能在窄侧栏里用"的一页。

### 它让用户能做的那件事：发布 / 编辑公告

> 因为公告那件事的规矩本来就是"只有用户能发布和改" ——
> 把"发布"做成界面上的一个按钮，比"让用户去改文件"更符合那条规矩。

⚠️ 但别说成"唯一的写入口" —— 实际有三个，**只有面板这一条有技术闸门**：

| # | 写入口 | 技术闸门 |
|---|---|---|
| 1 | 面板 | ⚠️ **发布没有确认框**（点了就提交）；**编辑和删除有**（先看"改前 / 改后"对照 ⇒ 确认才保存）。另有乐观锁：`revision` 对不上就拒 |
| 2 | `announce` 工具（任何一张桌） | ⚠️ 没有 —— 只在工具说明里写"先征得用户同意" |
| 3 | 直接改那个文件 | ⚠️ 没有（它就是个纯文本文件） |

⇒ 准确的说法："只有用户能批准"是一条约定，而面板是唯一把它做成结构的入口。
⇒ 但这不等于"从别处写不进去" —— 所以**别把它当成一道闸门来依赖**。

## 二、⭐ 边界：面板能写什么、不能写什么

这一节比界面长什么样重要得多。

| | |
|---|---|
| ✅ 能写公告 | 但只有用户 —— 而且编辑要确认 + 两道乐观锁（见下） |
| ✅ 能删公告 | 见 §三。删不属于"例外" —— 它是"**AI 只能追加，用户可以删改**"里属于用户的那一半 |
| ⛔ **永不写"投递状态表"** | 那是派生视图（投递插件生成的）。面板一写，就有了第二个真相源 |
| ⛔ **没有登录/权限系统** | "只有用户能改"靠的是：这是他专用的界面 + 编辑要确认 + 乐观锁 |

写接口的四道护栏（写文件是事故级的事，所以格外硬）：

| # | 护栏 | 为什么 |
|---|---|---|
| 1 | ⭐ 原子写（先写临时文件 → `rename`） | 公告文件是各桌获取办公室信息的唯一入口。半截文件 = 各桌再也收不到公告 = 事故 |
| 2 | ⭐⭐ 两道乐观锁 | ① `revision` = 整个文件的指纹 ② 编辑/删除时要逐字等于文件里那一行。**任何一道对不上就拒绝**，绝不猜"大概是想改那条吧" |
| 3 | 只认本机同源 | 防的不是黑客，是你浏览器里别的网站顺手发个请求 |
| 4 | `allowWrite: false` 一键退回纯只读（**包括删除**） | 有些环境就是不该让面板写 |

> ⚠️ 这里列 4 条，而 [`02`](02-三个插件分别是什么.md) 列 5 条 —— 不是矛盾，是分工：
> `02` 那份是给"想改代码的人"看的总表，而这份把"删除要有据"放到 §三去讲了。

> ⚠️ 一条反直觉的：平台的审批服务在"完全权限"模式下会静默通过 ⇒ 它拦不住误点。
> 所以"编辑要确认"只能靠界面上的确认框。**别把平台审批当成一层保护。**

## 三、⭐ "删除公告"这个决定

> 一句话："撤回"被否掉了，做的是真删；而"真删"缺的那一半（见过的人不会收到信号）
> 用"删之前告诉你几个人见过 + 删之后留一行记录"来补。

它和那条"AI 只能追加"的规矩是什么关系：

```text
旧说法：公告文件"只增不改"        ⇒ 删除是"破坏规矩"（于是它成了一个例外）
新说法：AI 只能追加；用户可以删改    ⇒ 删除属于用户那一半（于是它不再是例外）
```

⇒ 而"用户可以删改"本来就在规矩里（[`01`](01-思路.md) §五.二一直写着 *"只有用户能删改已有的行"*）——
只是旧名字把它盖住了。

⚠️ 而"删掉一行"比"改一行"更狠：

| | 读者会收到什么信号 |
|---|---|
| 改一行 | ✅ 一个全新的行（指纹变了）⇒ 它会被当成新公告再推一次 |
| 删一行 | ❌ 什么都没有 —— 他上下文里还留着那条，而且**永远不会知道它被撤了** |

⇒ 那不是"污染"，是"分歧"：你说"那条我删了"，而某个会话还按它做着事。

而"用户在环上"正是为这件事准备的：删除不是日常动作，
确认框里会告诉你有几个会话见过这条，删之后往 `公告-删除记录.md` 追一行。
⇒ 我不假装删除没有代价，只是让它有据、有痕、有人在场。

### 为什么不做"撤回"

"撤回"的样子：那一行留在原地，有效期栏写成 `撤回` ——
这样已经见过它的会话下一步会收到一句"这条已撤回"，历史也完整。

否掉的理由：

> *"真正有用的公告不会被撤回和删除，没用的公告也不会被留着几天之后才撤回和删除。"*

⇒ "撤回"这个状态在现实中根本不会被用到 ——
那就是一个多余的机制（正是 [`05`](05-取舍与放弃.md) 里砍掉的那一类）。

### 三档，不是一个数

| 情况 | `seenBy` | 界面 |
|---|---|---|
| 问到了，有会话见过 | `≥1` | "有 N 个会话见过这条" |
| 问到了，确实没人见过 | `0` | "没有任何会话的「见过」记录里有这条" |
| 问不到（接口没应答） | `null` | "问不到 —— 这不代表没人见过" |

⚠️ 这里有一条值得单独记的教训：

> 一个"永远偏低甚至恒为 0"的数字，比没有这个数字更危险 ——
> 它会让你放心地删掉有人记得的东西。

⇒ 所以"问不到"**绝不能显示成**"没人见过"：那会把"我不知道"说成"没人在意，放心删"。
⇒ 那是这个功能最危险的一种失败。

### ⚠️ 三件"删除的代价"，用的时候要知道

| # | 事实 |
|---|---|
| 1 | 删掉之后，公告文件里没有痕迹 —— 那是"真删"的意思。但面板会往 `公告-删除记录.md` 追一行（`当时见过数 ｜ 被删的那一行原文`）⇒ "某条怎么没了"是查得到的 |
| 2 | **那个数字会偏大**：seen 记录是累积的，不清理已消失的会话。公告插件会尽量用平台名单滤掉，但拿不到名单时就不过滤，而且会在界面上说明（`seenByFiltered: false`） |
| 3 | 记录里的时间是"本地时间 + 时区偏移"（形如 `2026-10-01 11:58:09-07:00`）—— 人能直接对上自己的钟，机器能无歧义还原。<br>⚠️ **如果那份记录文件是更早的版本写的**，时间可能是不带标记的 UTC（和本地时间差几小时，还可能跨天）—— 别把两种混着比 |

⇒ 所以它是一个"够用来提醒"的数字，不是一个统计量。

### ⚠️ 删除失败时，界面会说清"能不能确定"

这条值得单独写，因为它是一个"诚实"的设计：

| 能不能确定 | 界面说 |
|---|---|
| 能确定没删（路由不存在 / 403 / 后端按约定回了 `ok:false`） | "这一次没删" |
| 确定不了（连不上 / 2xx 但不是约定的 JSON / 5xx 且不是 JSON） | "删没删成说不准 —— 刷新看看" |

⇒ 第二种情况**绝不能说"没成功"** —— 那会让用户再点一次，而第一次可能已经删掉了。
（"删成功了却报失败" 和 "报成功了其实没删" 一样坏。）

### 删除记录长什么样（「健康」页里的一条时间线）

它不是一个表格，是一条时间线 —— 按本地日期分组（和公告页的「今天 · 10-01」同一套分隔线），
左边一根竖线，每条一个点。点的样子就是"见过数"那一档：

| 点的样子 | 意思 |
|---|---|
| **实心（强调色 `--oap-accent`）** | 有会话见过这条 —— ⚠️ **这一档刻意用强调色，不用警告色**：<br>这条记录说的是"'有人见过'这个事实"，**不是"出事了"** —— 用警告色是把它当成了告警 |
| 空心 | 没人见过 |
| 虚线圈 | 当时没问出来 |

每条上还有什么：

| 元素 | 说明 |
|---|---|
| 右上角一颗标签 | `3 个会话见过` / `没人见过` / `当时没问出来` |
| 节标题上一句汇总 | "其中 K 条删的时候有会话见过" |
| 被删的那一行拆开显示 | 发布者 / 一句话 / 发布于 / 原定有效期 / 详见 —— 拆不开就用等宽字原样显示 |
| 「复制原文」 | 误删了想恢复：**把那一行贴回公告文件末尾**就行 |
| ⚠️ 「可能被截过」 | 记录本身被截过时标出来（这时不显示"原定" —— 截口可能正好落在有效期中间）。<br>⚠️ **只会出现在更早版本写下的记录里** —— 现在的记录**整行存**，不会截；早期那种"只存前 120 字"的才会被截 |
| 默认露 6 条 | 下面是「展开其余 N 条」；接口最多给 50 条，文件里更多时底下会明说"更早的 N 条只在记录文件里" |
| 搜索框 | 超过 6 条、或者从公告页带着词跳过来时出现；能搜删掉的内容、发布者、日期和时间 |

### 公告卡片上也直接显示"有几个会话见过"

哪个会话的「见过」记录里有它，卡片右上角就有一颗标签 ——
`3 个会话见过` / `还没人见过` / `问不到见过数`（三档，**`null` 绝不显示成 0**）。

⚠️ 为什么这一颗要有：那个数原来只出现在两个地方 ——
删除确认框里、以及删完之后的记录里。
⇒ 想知道"这条有多少读者"，得先走到"要删它"那一步 —— 那个顺序不对。
⇒ 所以它现在就在卡片上，和「新」标签并排（一个说"我看过没"，一个说"多少人看过"）。

### ⚠️⚠️ 而这个数是什么口径，要说清（它不等于"谁读过"）

**它是一个"记录"口径，不是一个"阅读"口径** —— 说清这件事，是因为它很容易被读过头：

| 它是 | 它不是 |
|---|---|
| 有几个会话的「见过」记录里有这条 | ⛔ 不等于"这条正文被展示给了几个会话" |
| —— | ⛔ 更不等于"几个会话读了、理解了、照它做了" |

⚠️ **两个机制会让它和"真读过"不一样，而且方向相反**：

| 机制 | 它让这个数…… | 所以 |
|---|---|---|
| ⚠️ **整批记账**（开桌时一次最多展开 8 条，而**记账是整批的**） | **偏多** —— 同时有 9 条新公告时，正文只展开 8 条，**而 9 条都会进那个会话的 seen 记录** | **它 ≥ "真被摊开过的条数"** ⇒ ⛔ **造不出假的 0** |
| ⚠️⚠️ **会话压缩后清空重记** | **偏少** —— "见过的"随上下文一起没了，插件会清空这本账重记；**而已经过期的条目不会再记回去** | ✅ **这才是让 `0` 失真的那个** |

**⚠️ 而"整批记账"是刻意的、也没打算改**：反过来（只记展开过的那几条）会让
被截掉的那些每一步都重新来一遍 —— **那是活锁。** ⇒ 这是一个取舍，代价就是上面那条差距。

**⭐ 而别把 `0` 失真归给"数量上限"** —— 数量上限只会让它**偏多**，造不出假的 `0`。
**⇒ 一个理由引错了机制，比不给理由更糟**（它会让人以为自己懂了）。**真正的原因是"压缩重记"。**

所以用它的正确姿势：

> 拿它当"提醒" —— *"这条有人在看，删之前想一下"*。
> 别拿它当"证据" —— ⛔ **尤其别用"没人见过"来宣称"可以放心删"**。
> `还没人见过` 只说明没有会话的账上有它；而账上有它，也不代表那条正文真的被摊开过。

⚠️ 而它和删除记录里那颗的措辞不同，因为时间点不同：

| 标签 | 说的是哪个时刻 |
|---|---|
| 卡片上那颗 | 现在 |
| 删除记录里那颗（`当时没问出来`） | 删的那一刻（那是记录下来的快照）

三处"小连接"（都很低调，但有用）：

| # | 在哪 | 是什么 |
|---|---|---|
| 1 | 公告页那行"共 8 条 · 最新在前"后面 | 「· 删过 7 条」—— 点了直接到删除记录 |
| 2 | 公告页搜索、而且搜不到时 | 列表下面说一句"它可能被删了：删除记录里有 N 条匹配「…」"，点一下带着搜索词跳过去 |
| 3 | 删完的提示 | 面板会先核对删除记录里真有这一笔，再说"已删除 · 记在「健康」页的删除记录里"（后端回了 `logged` 就直接照它说） |

> 第 2 条那个方向是反着做的，而它比"正着"更有用：
> 记录里没存行号（存了也会漂），所以"跳到那条公告留下的空白处"做不到。
> 而"搜一条搜不到时，人最想知道'它去哪了'" —— 那个方向做得到。

「健康」页还有一行「见过数」，回答"确认框里那个数能不能信"：

| 显示 | 意思 |
|---|---|
| "由公告插件统计，按 N 个会话算" | 拿到了会话名单 ⇒ 按名单统计的 seen 记录（⚠️ 仍不证明正文已逐条展示或被理解，见上面那一节） |
| "没拿到平台的会话名单 …… 数字可能偏大" | 退回累积计数（见上面"三件删除的代价"第 2 条） |
| "问不到 —— 公告插件的「见过」接口没应答" | `null`，不是 0 |

## 四、架构：两半，靠一个很窄的接口相连

```
plugins/dsh-bulletin-panel/
├─ index.js    ← 宿主半边（Node 进程）：读文件、暴露 HTTP 路由、处理"发布/编辑/删除"
└─ client.js   ← 客户端半边（浏览器）：画界面、fetch 那些路由
```

⚠️ 这两半互不引用 —— 它们只通过接口说话：

```
GET  /sidebar/api/office                 →  公告条目 + 状态表 markdown + 文件指纹 + canWrite + 版本号 + 见过数
GET  /sidebar/api/office/deletions       →  删除记录（面板「健康」页把它画成一条时间线）
POST /sidebar/api/office/announce        →  追加一条公告
POST /sidebar/api/office/announce/edit   →  改一条已有公告（逐字核对原文）
POST /sidebar/api/office/announce/delete →  删掉一条公告；回应里带 `logged`（删除记录写上了没有）
```

⚠️ 另外还有一条不在这个文件里：`GET /sidebar/api/announce/seen`
—— 那是公告插件注册的（面板后端去调它，把结果并进第一条响应）。
⇒ 所以"两半"其实牵扯到三个包。

而"窄"这件事是刻意的：改前端不需要碰后端，改后端也不需要碰前端。

| 好处 | 说明 |
|---|---|
| 前端可以从零重写，后端一行不动 | 两边只靠契约通信 —— 重写一边不用碰另一边 |
| 前端改坏了只影响那张卡片 | 宿主和后端插件都活着，控制台报一句 `slot entry crashed` |
| 契约可以先定、再各做各的 | 和前端先定接口，然后同时开工 —— 没有返工 |

## 五、⭐ 想改前端的话：几件必须知道的事

前端就是 `client.js` 一个文件（纯 JS，没有构建步骤）。
改它不影响任何后端功能 —— 你随便重写。只有下面这些动不得。

### 5.1 ⛔ 五条"碰了就坏"

| # | 约束 | 为什么 |
|---|---|---|
| 1 | 别改 `fetch` 的**地址与字段名** | 前后端只有这一个接口 —— 改了数据就接不上，卡片变空白 |
| 2 | 别改 `registerTab` 的 `id` | 那是卡片的身份。改了等于新开一张；而且**同一个 id 注册两次会直接抛错** |
| 3 | ⛔ 别 `require('@deepseek-ai/dsh-client-ui-*')` | 那些是**内部包**，会无声变化；而这个文件没有类型检查 ⇒ 一个抛错的组件会把整张卡片变空白。控件自己写 |
| 4 | ⛔ 别写死颜色 | 宿主有亮色/暗色两套 + 可换肤 ⇒ 写死了必然有一个不对 |
| 5 | 别改 `__ModuleLoader__.load({ id })` 里的 id | 同 #2 |

⚠️ 还有两条是"我们的约定"，不是平台要求（改它们之前先想清楚）：

| # | 约定 | 为什么守它 |
|---|---|---|
| 6 | `FE_VERSION` **必须和 `package.json` 的版本号一致** | 那个版本号是唯一能回答"我看的是哪一版"的东西（它必须和 `package.json` 一致，否则水印会撒谎） |
| 7 | `renderInline()` 负责渲染 `**粗体**` 和 `` `代码` `` —— 一条文案里带 markdown 时**必须过它** | 不过它，星号和反引号会原样显示在界面上 |

### 5.2 颜色只能用主题 token

宿主暴露的 CSS 变量就这么多（我们问过平台的检视器）：

```css
--dsw-alias-bg-base / bg-layer-1 / bg-layer-2 / bg-overlay
--dsw-alias-border-l1 / border-l2
--dsw-alias-brand-primary
--dsw-alias-label-primary / label-secondary
--dsw-alias-state-success-primary / warn / error / idle
--dsw-specific-sidebar-fill
```

⇒ 层次感只能靠留白、字号、行高、透明度、圆角做。
但好处是：亮色/暗色/换肤自动全对，你一行都不用写。

#### ⚠️⚠️ 而有一个**明确的例外**：`--oap-accent`

```css
.oap-root {
  --oap-accent: color-mix(in oklab, #4d6bfe 82%, var(--dsw-alias-label-primary));
}
```

**⇒ 这是全前端唯一一处硬编码颜色**（`#4d6bfe`），而**它是有意加的**：

| 问题 | 为什么要它 |
|---|---|
| **面板要一个"强调色"** | 但宿主暴露的 token 里**只有 `brand-primary`**，而它在侧边栏的底色上**偏淡、不够"强调"** |
| **为什么不直接用 `brand-primary`** | 试过 —— 那个"见过"的圆点和小标签**在亮色主题下几乎看不见** |
| ⭐ **而它是 `color-mix` 出来的** | **不是写死一个颜色** —— 它**跟着宿主的主文字色走**，所以**换肤/暗色下自己会变** |

**⚠️ 所以：**

| 你要改前端 | 怎么做 |
|---|---|
| **看见 `#4d6bfe`** | ⛔ **别当成"违规写死颜色"删掉** —— 那是**有意留的例外**（删了那三档标记就看不见了） |
| **想换回纯 token** | 一行就行：`--oap-accent: var(--dsw-alias-brand-primary);`（**代价见上表**） |
| **想再硬编码别的颜色** | ⛔ **别** —— **例外只有一个，而且它必须走 `color-mix`** |

> ⚠️ **而这条有自测守着**：`test-bulletin-panel.mjs` 里有一条断言 ——
> **`client.js` 里出现的每一个十六进制颜色，都必须在允许清单里**。
> **⇒ 你想加第二个硬编码颜色，那条断言会当场红。**

> ⚠️ 一个具体教训：行内代码（`code`）的底色别用一块中性的灰（`bg-layer-2`）——
> 放进彩色文字里（比如确认框那句警告色的提示），暗色主题下会变成
> "一块灰底 + 一段橙字"，看起来像个按钮（而它点不了）。
> ⇒ 用 `color-mix(in oklab, currentColor 10%, transparent)`：底色跟着它所在那段文字的颜色走。

### 5.3 改完怎么验

> ⚠️ 这里写的是"改代码的人在自己机器上怎么验"，用的是本机的插件管理器。
> 给别人装的路径不一样（`dsh plugin --profile <名字> add file:./plugins/…`）—— 那在根 [`README`](../README.md) 的「快速开始」里。

```
① node --check plugins/dsh-bulletin-panel/client.js
② 装：plugin_manager install_bundle → 目标目录 plugins/dsh-bulletin-panel
      ⚠️ 改 client.js 也要 +1 版本号；替换已装的包要重启 DSH 才进新代际
③ 浏览器硬刷新（Ctrl+Shift+R）→ 右侧栏「办公室」
      ⚠️ 打开控制台看有没有 `slot entry crashed` —— 有就是组件抛错了
④ 确定"公告协议没被改坏"（仓库里没有测试，所以要手工确认一件事）：
      面板写出的行必须正好 5 段（`- 日期｜发布者｜一句话｜详见｜有效期`）。
      少一段，`dsh-bulletin-announce` 的正则就整条跳过、各桌静默收不到。
      ⇒ 改 `formatAnnounceLine` 或 `parseAnnouncements` 之后，务必各发一条试试。
```

> ⚠️ **`plugin_manager install_bundle` 是本机插件管理器那个动作的名字**（自测/开发时用）——
> **改成命令行就是 `dsh plugin --profile <name> add file:./plugins/dsh-bulletin-panel`**
> （⚠️ **`file:` 前缀不能省** —— 直接写目录路径等于建符号链接，不会装插件自己的依赖）。
> **"新代际"是插件管理器的说法**：它把每次安装放进一个**新的代际目录**，**重启之后才切过去**。
> **⇒ 你只要记住"改完要重启"就够了。**

> ⚠️ 关于测试：这份仓库不含测试（理由见 [`05`](05-取舍与放弃.md) 末尾），
> 所以上面第 ④ 条只能手工确认。

## 六、⚠️ 一个真实的产品教训："数据对"和"看起来对"是两件事

背景：有个报告说"投递那里，取走的会话和投单的会话是一样的"。

数据从头到尾都是对的。 真正的问题是两处显示决定叠在一起：

| # | 显示决定 | 后果 |
|---|---|---|
| 1 | 卡片标题显示"单子投给哪张桌"，但没写明（没有动词） | 看起来像"谁投的" |
| 2 | "取走的会话"和标题是同一张桌时，它把桌号省了、只留会话名 | 标题 `03 本机维护` 与下面那行 `本机维护` 摆在一起，看起来就是同一张桌 |

⇒ 读者看到的是一个"不存在的矛盾"。

由此得三条：

| # | |
|---|---|
| 1 | 一个**没有动词的列标题**，会被读成另一个意思。 写「目标桌」不够，要写「投给」 |
| 2 | "为了简洁而省略"是有风险的 —— 省掉的那个信息，可能正是读者用来判断上下文的那一个 |
| 3 | ✅ "看起来一样"这种报告是有效的 —— 报告人没说"字段取错了"，他说的是现象，而现象是真的 |

⚠️ 而当时还有一个错诊断：看到截图上的值恰好等于 `source`，
就断定"前端把 source 显示成取走方了" —— 而面板手里根本没有 `source`。
⇒ **"两个值相等"不等于"它们同源"**（详见 [`06`](06-经验与教训.md) 误判四）。

后来怎么修的：

| # | 改动 |
|---|---|
| 1 | 标题加动词：「投给 [02] 环境维护」 |
| 2 | 「取走的会话」一律写全、带桌号（不再为了简洁而省略） |
| 3 | 后端那两张表加了「谁投的」一列 —— 读者不用再猜"这张单子是谁发起的" |

## 七、一条值得抄的经验

**先定接口，再写前端。**

前后端只有那一个契约（地址、字段名、失败码都定死了）——
它定死了，两边就能同时干、还能换人干。
