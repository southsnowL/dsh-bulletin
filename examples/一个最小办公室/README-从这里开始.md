# 一个最小办公室（示例骨架）

> **这个目录是拿来抄的，不是拿来跑的。**
>
> 把 `00-通用\`、`交付区\` 和你的桌目录**复制到你选定的办公室目录**，
> 改掉桌名和编号，就有一个能开始用的办公室了。
>
> ⚠️ **"办公室目录"不一定等于某个会话的工作区** ——
> 它就是你挑的一个地方，**各张桌的工作区留在原处**（见下面「它和会话的工作区是什么关系」）。
>
> **⚠️ 抄的时候顺手删掉那些 `说明-这里是空的.md`** ——
> 它们只是**占位文件**（见下面「关于那几个空目录」）。

---

## 如果你是这个电脑上的 agent：**这份就是给你的派单**

> **你是被派来布这个环境的。** 三件活：**建目录** → **装三个插件** → **写配置**。
> （安装和配置的具体形状，看仓库根 `README.md` 的「快速开始」那节。）

**动手之前，先跟派你的人确认两件事 —— 这两件你猜不出来**：

| 要问的 | 为什么猜不出来 |
|---|---|
| **办公室放哪个目录** | ⚠️ **它不一定是你的工作区** —— 各张桌的工作区可以各不相同，**办公室是另找一个中立地方**（见下面「它和会话的工作区是什么关系」） |
| **这台电脑上要哪几张桌、各叫什么** | 桌是"给人看的角色名"，**不是你能编的** |

**其余的你读得懂、也不用别人转述**：建哪些文件夹、文件里写什么、配置怎么填。

### ⭐ 它和会话的工作区是什么关系（**这一节就是上面那个"见下面"**）

**一句话：没关系。** "办公室"是一个**你自己挑的目录**，它**不必是任何会话的工作区。**

| | 是什么 | 能不能换 |
|---|---|---|
| **会话的工作区** | 那个会话干活的地方（`D:\MyGame`、`D:\Workbench`……） | 各会话各自的事，**布办公室时不用动它们** |
| ⭐ **办公室目录** | 上面那些会话**共用的那一小块**：公告文件、信箱、状态表、交付区 | **随便挑**（哪都行，只要大家写得到） |

**⇒ 所以有两种常见的摆法，都对**：

```
摆法一（共用一个大目录）              摆法二（各在各处，只共用办公室）
D:\my-office\                        D:\MyGame\        ← 桌 01 的工作区
├─ 00-通用\        ← 办公室          D:\Workbench\     ← 桌 02 的工作区
├─ 01-游戏开发\    ← 桌 01 的工作区    D:\my-office\     ← ⭐ 只有这一块是"办公室"
├─ 02-环境维护\    ← 桌 02 的工作区    └─ 00-通用\
└─ 交付区\                                ├─ 公告.md
                                          ├─ 信箱\01\ · 02\
                                          └─ 投递状态.md（插件生成）
```

**⚠️ 而摆法二有一个前提**：**各会话要写得到那个办公室目录** ——
**用默认的 `workspace-write` 权限时，模型的文件工具只能写本会话的工作区。**
**⇒ 见上面「各桌的会话写得到这个目录吗」那节。**
（**公告不受影响** —— 那是插件用宿主权限写的，不走会话的文件工具。）

**而布完之后**，还有一步别漏：
**发第一条公告，说清"办公室在哪、有哪几张桌"** ——
**那条公告就是"让这台电脑上所有会话知道有这间办公室"的那个动作**
（它们下一步就会看到；详见仓库根 `README.md` 那节）。

## 为什么需要"布一个环境"

**先说一件容易被误解的事**：

> **这套东西不是"装上插件就能用"的。**
> 它要求你**先在磁盘上布出一个环境** —— 一些目录、一份公告文件、每个参与者一个信箱。

**而这恰恰说明了它的性质**：

> **它是一份参考实现，不是一个即插即用的产品** —— 因为它依赖一套**约定**，
> 而约定**得有人接受**，不是能"生成"的东西。

**⚠️ 但"要布环境"不是它不适用的原因**：

| 容易以为的原因 | 为什么不对 |
|---|---|
| *"要布环境这一步，就注定了它不可能通用"* | **"要布环境"说的是"麻烦"，不是"不可能"** —— 麻烦只影响愿不愿意装，**不影响它能不能被抽象** |

**⭐ 真正的原因是**：**它依赖"会话标题带 `NN-` 前缀"这个约定**，而
**平台里没有"同时存在的几个平等会话"这个原语**（有父子关系，没有"对等"）⇒
**"对等"只能靠约定造出来。** 完整的辨析在仓库的 [`docs/01`](../../docs/01-思路.md) 和 [`docs/06`](../../docs/06-经验与教训.md)。

**⚠️ 但这不代表它没用** —— 它解决的是**一个真实且普遍**的问题：

> **几个对等的 AI 会话共用一台电脑、一个磁盘。**
> **它们不可能做到绝对独立** —— 有一些信息**必须**同步和共享。
> 这套目录结构就是那个"共享的方式"。

## 目录长什么样

```
<办公室目录>/                   ⭐ 你自己挑的地方（**不要求是某个会话的工作区**）
├─ 00-通用/                    ⭐ 共享目录
│   ├─ 公告.md                  办公室公告（**AI 只追加；用户可以删改**）
│   ├─ 投递状态.md              插件自动生成（**别手改**）
│   └─ 信箱/
│       ├─ 01/                  ← 桌 01 的信箱（**别人只能放，只有主人读**）
│       └─ 02/                  ← 桌 02 的信箱
├─ 01-示例桌甲/                  ← 桌 01 自己的工作目录（⚠️ **可选的布局**）
├─ 02-示例桌乙/                  ← 桌 02 自己的工作目录（⚠️ **可选的布局**）
└─ 交付区/                       ← 给**用户**的成品（"出件口"）
```

**⚠️ 上面那两个 `0N-示例桌N/` 是"可选布局"，不是要求** ——
**几张桌共用一个目录时把它们放这儿很方便；而各桌用自己的工程目录（`D:\MyGame` 之类）也完全可以。**
**⇒ 唯一必须在这个目录下面的是 `00-通用\`（和可选的 `交付区\`）。**

### ⚠️ 而有一件事得先确认：**各桌的会话写得到这个目录吗**

**这一条最容易漏，而漏了会在"第一次往信箱放文件"时撞上**：

| 情况 | 会怎样 |
|---|---|
| **各桌工作区都在办公室目录里**（就是上面那种布局） | ✅ **没问题** —— 它们本来就在自己的可写范围内 |
| **各桌工作区各在一处**（比如 `D:\MyGame`），**办公室在别处** | ⚠️ **要看权限**：用默认的 `workspace-write` 时，**模型的文件工具只能写本会话的工作区** ⇒ **往办公室信箱写文件会被拒** |

**而有一个容易误会的对照**：

> **`announce` 工具能跨工作区发公告** —— 因为**插件走的是宿主权限的读文件/写文件，不是模型的文件工具。**
> **⇒ 但"往信箱放一份文件"没有这样一条通道** —— **那要靠会话自己的文件工具。**

**⇒ 所以要么让办公室落在大家写得着的地方，要么把通道收窄成"公告 + 单子"**
（**单子本来就是"一句话 + 一个指针"，不搬文件也能用**）。

**四条规矩（就这四条）**：

| 你想干的事 | 放哪 |
|---|---|
| 给自己干活 | **自己的目录** |
| **给别人东西** | **对方的信箱**（**所有权当场转移** —— 不要"放自己家叫他来拿"） |
| 给**所有人**的东西 | **`00-通用\`** |
| 给**用户**的成品 | **交付区** |

### 关于那几个空目录

**你会发现几个目录是空的，里面只有一个 `说明-这里是空的.md`。**

**那不是给你看的规矩，是给 git 看的**：

> **git 只跟踪文件，不跟踪目录** ⇒ **空目录在仓库里会直接消失**。
> 所以每个空目录里放一个占位文件，把目录"撑"住。

**⇒ 你抄走的时候，把它们删掉就行**（那几份说明里也这么写了）。
**顺带一提**：这也是"示例骨架"这种东西在 git 里最常踩的坑 —— **不占位，抄下来就少一半目录。**

## 三步就能开始

### 第 1 步：把骨架抄到办公室目录

```sh
# ① 先站到示例目录里（下面几条相对路径都以它为起点）
cd examples/一个最小办公室          # ← 这一条在 dsh-bulletin 仓库根目录下执行

# ② 建好你的办公室目录（⚠️ 必须先建：cp 最后那个参数是"往哪个目录里放"）
mkdir -p ~/my-office

# ③ 抄共享目录和交付区（`00-通用` 里的 `信箱/01`、`信箱/02` 会跟着一起过去）
cp -r 00-通用 交付区 ~/my-office/

# ④ 建两张桌的工作目录（名字里的编号要和信箱对上）
mkdir -p ~/my-office/01-你的第一张桌 ~/my-office/02-第二张桌

# ⑤ 以后想加第三张桌，就连信箱一起加
mkdir -p ~/my-office/00-通用/信箱/03
```

**⚠️ 两个会让你多看到一条报错的地方**：

| 报错 | 为什么 / 怎么办 |
|---|---|
| `mkdir: …/信箱/01: File exists` | ⛔ **不要再建 `信箱/01`、`信箱/02`** —— 它们**已经跟着 `00-通用` 抄过去了**。想确认就 `ls ~/my-office/00-通用/信箱/` 看一眼 |
| `No such file or directory` | ⚠️ **`mkdir` 不加 `-p`，父目录不存在就直接失败**（`cp` 的目标目录不存在也一样）—— 所以第 ② 步不能省 |

### 第 2 步：写一份公告文件

**公告文件必须有个"头部说明"** —— 因为**各桌的 AI 会读它**，得让它知道格式和规矩。
抄 `00-通用\公告.md` 这份示例就行（里面就是头部说明 + 一条示例条目）。

### 第 3 步：把会话标题改成 `NN-名字`

```
✅ 01-前端
✅ 02-后端
❌ 随便聊聊          ← 认不出桌 ⇒ **它不是办公室成员**：不记进状态表、也收不到单子
```

**⚠️ 上面那个 `❌` 要说清是"哪一档"**：

| | |
|---|---|
| **它照收公告** | ✅ 公告是广播 —— **入口不该关**（新会话要靠它才知道有这间办公室、才知道该改标题） |
| **它收不到单子** | ⛔ **不知道它是谁，就不能把活交给它** |
| **它不记进「认过桌的会话」** | ⛔ ⚠️ **这一档是后加的** —— 它**原来会被记成一个叫"办公室"的桌**，于是**看起来像个成员、而实际取不到任何单子** |

**⚠️ 这一步是整套东西的起点** —— "桌"这个概念**就是从标题前缀来的**。
平台里没有"桌"这种东西，**是我用命名约定造出来的**。

**⚠️ 顺序不能反**：新会话**不能一开出来就改名** —— 得**先发一条消息**（平台这时才有真实会话和自动标题），
**然后**把标题改成 `01-名字`。**判据是硬的**（不用"试试看"）：

> 改名之后的**下一轮**，那个会话会收到一条注入：
> `（跨桌投递：本会话认作 **桌 01** —— 从会话标题「01-名字」读出来的。本桌的投递单会送到这里。）`
>
> ✅ **出现这一句 = 认桌成功**；❌ **一直不出现 = 标题前缀不对**（不是两位数、缺 `-`、或者改的不是会话标题）。

## 这里有哪些是**必须**的、哪些是**可以改**的

| 东西                 | 必须吗                              | 能改吗                 |
| ------------------ | -------------------------------- | ------------------- |
| **一个共享目录**         | ✅ 必须（**但名字随便**，`00-通用` 只是我自己的叫法） | ✅ 改配置               |
| **每个参与者一个信箱**      | ✅ 必须（投递的落点）                      | ✅ 目录名可改             |
| **会话标题带 `NN-` 前缀** | ✅ **必须** —— 认桌靠它                 | ❌ **不能改**（这是"桌"的定义） |
| **公告文件的路径**        | ✅ 必须有这个文件                        | ✅ 改配置               |
| **`交付区`**          | 🟡 建议有（给用户的东西要有地方放）              | ✅ 随便                |
| **四个桌 / 四个编号**     | ❌ 不必须 —— **两张桌也完全能用**            | ✅ 随便几张              |

## 常见问题

**Q：我只有一张桌，能用吗？**
能用，但**意义不大** —— 这套东西的价值在"**桌与桌之间**"。一张桌的话，投递无处可投。

**Q：桌和"项目"是什么关系？**
**没关系。** 桌是**参与者**（一个长期存在的角色），项目是**活**。
一张桌可以同时管好几个项目；一个项目也可以有几张桌参与。
（我自己的做法：**桌 ≈ 一个长期的工作主题**。）

**Q：为什么不让每个会话自己看别人的目录？**
因为那会长成一大片耦合 ——
**实测代价：原本只是想把两个收件目录搬个家，全办公室有 82 处引用要跟着动。**
**⇒ 信箱那条规矩（"别人只能放、只有主人读"）就是为了把这件事掐死在源头。**

**Q：我一定要用 "信箱" 这个词吗？**
不用。它就是个"**别人的收件目录**"。叫什么都行 —— **只要规矩是"别人只能往里放"**。

## 下一步

1. 装 `dsh-bulletin-dispatch`（**先装这个** —— 它是认桌/投递的基础）
2. 把它指向你的办公室目录和桌名（配置见 `docs/02-三个插件分别是什么.md`）
3. 开一个新会话、**先发一条消息**，再把标题改成 `01-名字` —— **下一轮**它会收到"本会话认作 **桌 01**"那条注入（判据同上面第 3 步）
4. 再开一个 `02-名字`（同样**先发一条消息再改标题**），然后**从 01 用 `dispatch_ticket` 发一张单子给 `02`**
   —— ⚠️ **`desk` / `summary` / `ptr` 三个都必填**（`ptr` 指**一个已经存在的地方**；
   内容长的话，先按 `00-通用\信箱\README-信箱怎么用.md` 的命名写进 02 的信箱，再指向它）；
   接着**回到 02 那个会话、让它跑下一轮**，它的系统提示里会出现这样一段：

```
跨桌投递：本桌有 1 张待取的单子（桌 02）
· 来自 桌 01（09-30 13:47）：一句话 —— 详见 `00-通用\信箱\02\来自01-委托-窗口性能问题-20261001.md`
取走后本桌其它会话不会再看到它。要用就用，不用就放过 —— 不需要回执。
```

**⇒ 看到这一段，这套东西就跑起来了。**

**⚠️ 而"取走"是一次性的**：再让 02 跑一轮，那一段**不会再出现**（`list_tickets` 也会回"没有待取的单子"）——
**取走之后就没了**，想回看得去看 `00-通用\投递状态.md`。
